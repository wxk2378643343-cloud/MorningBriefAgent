# MorningBriefAgent 产品定义

- 版本：v1.0
- 状态：已确认（2026-11-05）
- 上游分析：`docs/product/requirements-analysis.md`
- 本文是产品层的事实源。与架构文档冲突时，先看 ADR，再看本文，再改下层文档。

---

## 1. 一句话定义

> 给一个 Windows 个人用户，在不依赖云服务的前提下，把「手机上随手说一句」变成「本地可查、可改、可复盘的结构化事实」。

不是通用聊天机器人，不是 SaaS，不是团队协作工具。

## 2. 用户

| 维度 | 事实 |
| --- | --- |
| 用户数量 | 1 人（作者本人）。本文所有取舍以此为前提 |
| 设备 | Windows 10/11 主力机 + 手机（飞书） |
| 使用节奏 | 早上看计划 → 白天手机随手记 → 晚上复盘 |
| 数据敏感度 | 高。全部数据留在本机，不依赖云端才能使用 |
| 技术能力 | 能自己装环境、看日志、改配置；不需要"傻瓜化"到零配置 |

**推论**：不追求"任何人装上就能用"。追求"我自己每天愿意打开"。

## 3. 入口分工（本文最重要的一节）

| 场景 | 入口 | 职责 | 明确不做 |
| --- | --- | --- | --- |
| 手机随手记、日程提醒、热量确认 | **飞书** | 自然语言输入，卡片输出，任务/日历同步 | 不做复杂编辑、不做批量管理 |
| 查看、编辑、复盘、配置 | **桌面端** | 结构化 CRUD、审计留痕、工作区与渠道配置 | 不复制业务规则，不直连 SQLite |
| 定时触发 | **Windows 计划任务 / 工作流** | 按时间跑 `todo-morning` / `todo-evening` | 不做常驻调度服务 |
| 唯一事实源 | **SQLite** | 待办、日程、饮食、审计、幂等、Outbox | 不被 Markdown 或飞书反向覆盖 |

两条铁律：

1. **同一业务规则只允许实现一次**，飞书与桌面都调用 `services/`，不各写一套。
2. **飞书是输入通道，不是事实源**。飞书里的消息、卡片状态都不能成为业务事实，必须落 SQLite 才算数。

## 4. 价值主张

1. **零手动整理**：资料与一句话进去，计划与结构出来。
2. **零云端依赖**：断网仍能看今天、改待办、做复盘（新闻/行情/飞书除外）。
3. **零信息丢失**：确认过的事实有审计，删掉的文件能恢复，失败的同步能重放。

## 5. 范围

### 范围内（当前投入）

- 首次引导（工作区 → Provider → 渠道 → 档案）
- 今日视图、待办、日程、日复盘
- Agent 计划生成（早间 / 晚间）
- 飞书：消息入口、卡片推送、任务与日历同步
- 本地结构化事实与审计

### 范围外（明确不做，避免反复讨论）

- 多用户、账号体系、权限模型
- 云同步、移动 App、Web 版
- 插件市场、第三方扩展协议
- 面向他人的 SaaS / 收费版本
- 面向普通用户的数据库编辑器
- 微信复盘、新闻、健身、基金的桌面化（保留 CLI，不投入界面）

## 6. 成功标准

两周后复核，四条同时成立才算产品方向正确：

| # | 标准 | 度量方式 |
| --- | --- | --- |
| 1 | 连续 7 天，每天至少打开桌面端 1 次 | 使用记录 / 自述 |
| 2 | 过程中**没有一次"想用但点不到"** | 摩擦日志（M1 后开始记） |
| 3 | 早间计划生成 10 次，≥ 9 次产出可直接采纳的计划 | 工作流运行记录 |
| 4 | 所有写操作都有明确的成功/失败反馈，零静默失败 | 代码审查 + 手动走查 |

## 7. 非目标（防止跑偏）

- 不追求界面精美度超过「顺手」。
- 不为"未来可能的平台化"提前抽象。Provider / Channel 保持现状，直到出现第二个真实实现。
- 不把"用了 Agent"当作卖点，Agent 只是实现手段。
- 不用"代码量、测试数、页面数"证明进展，只用闭环是否跑通。

## 8. 当前阶段

**M1：让产品诚实。** 不做新功能，只消除"看起来有、点了没反应"的落差。详见 `docs/product/m1-prd.md`。
