## 1. 背景与问题

### 1.1 现状

日常信息分散在三处：脑子里的临时记忆、手机聊天窗口、桌面待办软件。三个地方都不完整：

- 脑子记不住超过一天的事，尤其"路上想到的一句"。
- 聊天窗口能记，但找不回来，也没法按天回看。
- 待办软件要求先填表单、选分类、定时间——**记一条的成本高于不记**。

结果是：真正想记的东西大多没被记下来；记下来的那部分散落在各处，等于没记。

### 1.2 问题的本质

不是"缺一个待办工具"，而是**缺一个入口成本足够低、且事后能原样找回的地方**。

判断标准很硬：如果记一条要超过 5 秒、要选分类、要切 App，那它就不会被使用。反过来，如果记下来的东西找不回、看不全，那记了也没用。

### 1.3 为什么这是第一优先级

后续想做的事（早上给计划、晚上给整理）都建立在记录之上：

```text
记录（数据在） → 计划（今天做什么） → 整理（这一天是什么样）
   必须先做         依赖记录质量         依赖记录完整度
```

记录不完整时做计划，等于给一个不存在的"我"排日程；记录不准确时做整理，等于编故事。**所以 P0 只做一件事：把数据可靠地记进去、准确地取回来。**

## 2. 目标与非目标

### 2.1 目标（P0 要达成的）

| # | 目标 | 可判定标准 |
| --- | --- | --- |
| G1 | 记录不丢 | 连续 14 天，每天 ≥5 条，无一条丢失 |
| G2 | 记录不重复 | 同一条消息被记两次即为失败（0 容忍） |
| G3 | 记录不变形 | 存的文字与发送时逐字一致；存的图片与发送时字节一致 |
| G4 | 取得回 | 任意历史记录 5 秒内能搜到并打开 |
| G5 | 入口足够低 | 从打开飞书到看到回执 ≤ 5 秒、≤ 1 句话 |
| G6 | 失败可见 | 任何失败都出现在回执上，不允许只写日志 |

### 2.2 非目标（P0 明确不做，且不接受"顺手加一下"）

| 不做 | 理由 |
| --- | --- |
| 早间计划、件数计算 | P1，依赖记录质量 |
| 每日整理、周报、任何形式的"复盘"/打分/建议 | P2。且"复盘"本身带有评价意味，与"只记录事实"的定位冲突 |
| 完成状态流转、拖延统计 | P1。P0 记录的是"我说过什么"，不是"我做完没有" |
| OCR、图片内容识别、相似图去重 | P1 解析增强。P0 图片只要求"原样存、能打开" |
| 图片压缩、缩略图预生成、EXIF 清理 | P0 只做"能看"，不做"优化" |
| 多用户、账号、权限、云同步、移动 App、公网访问 | 单用户本地工具，引入这些会改变产品形态 |
| 新闻、行情、基金、健身、饮食、微信聊天分析 | 与"记下我说的话"无关 |
| 知识库文件管理、文件夹同步、数据库浏览器、工作流调度中心 | 同上 |
| 图表、统计报表、连续打卡 | 装饰，不影响记录可靠性 |

判断口径统一为一句：**不影响"我能不能把文字和图片完整地记进去"的，一律不做。**

### 2.3 存量能力的处置

已确认：**全部下线，且不做代码移植。**

- 旧实现不作为新基础。需要某个能力时按新规格重写——移植会连带继承旧的表结构、状态机与交互假设。
- 旧数据不迁移、不兼容。P0 使用独立数据文件与独立附件目录，与历史运行数据隔离。
- 旧代码暂不删除，作为只读参考；P0 验收通过后单独决定去留。

## 3. 用户与场景

### 3.1 用户

**只有一个人**：Windows 10/11 为主力机、同时使用 Linux 或 macOS 的个人用户（即产品负责人本人）。技术背景足够自己部署，但**日常使用时不希望碰到任何技术细节**。

用户特征直接决定了两条设计约束：

1. 不会为了记录而打开电脑——手机侧必须能独立完成"说一句"。
2. 不会容忍"点了没反应"——所有操作必须有明确反馈。

### 3.2 核心场景（P0 只有这四个）

| 场景 | 触发 | 用户动作 | 系统应答 | 成功感受 |
| --- | --- | --- | --- | --- |
| **S1 随手记一句** | 通勤路上想到一件事 | 在飞书发一句话 | 5 秒内回卡片：记下了 + 解析成了什么 | "不用切 App，也不用选分类" |
| **S2 拍张照存下** | 会议白板、纸质材料、快递单 | 发 1–9 张图（可带一句话） | 回卡片：图片 × N 已存，几张失败 | "图不会因为聊天记录清空而消失" |
| **S3 回头找一条** | 想找上周记的某个电话/地址 | 打开本地记录页，搜关键词 | 5 秒内列出结果，点开看原图 | "记得大概内容就能找到" |
| **S4 改一个字** | 系统把"待办"判成了"记录" | 在记录页点一下改类型/标题/时间 | 立即生效，原文不动 | "判错不烦人，一秒钟能修" |

### 3.3 反场景（明确不支持的用法）

- 用它在手机上管理项目、分配任务给他人。
- 用它写长文、做笔记整理。
- 用它做知识库检索（P0 只按原文关键词搜）。
- 在电脑关机时依赖它自动推送任何内容（P0 无定时任务）。

### 4.2 需求详情

---

#### FR-1 文字消息接收与落库

**用户故事**：作为用户，我在飞书发一句话，希望它立刻被存下来，不需要任何额外操作。

**需求描述**

- 支持纯文字消息，长度上限 5000 字（超出截断并在回执中说明）。
- 收到消息后**先落原文，再做解析**。解析失败或超时，原文依然保存。
- 记录必须能追溯到来源消息，以便识别重复投递。

**边界条件**

| 情况 | 期望行为 |
| --- | --- |
| 文字为空（纯空格/纯表情） | 若是纯图片消息 → 正常按 S2 处理；若既无文字也无图 → 回执"没记到内容"，不入库 |
| 超长文字（>5000 字） | 保存前 5000 字，回执注明"已截断" |
| 含链接、代码块、换行 | 原样保存，不做任何格式化或替换 |
| 解析失败 | 原文照常入库，字段用默认值，回执注明"未识别，已原样保存" |

**验收标准**

- AC-1：连续发送 10 条不同内容的文字消息，10 条全部入库，且**逐字比对与发送内容完全一致**（含标点、空行、表情）。

---

#### FR-2 图片附件接收与原样保存

**用户故事**：作为用户，我把照片发给机器人，希望它原封不动地存到本地，随时能打开。

**需求描述**

- 支持单条消息携带 1–9 张图片，可同时带一段文字。
- 图片**原样保存原始字节**：不压缩、不裁切、不转格式、不改文件名编码。HEIC 也原样存。
- 保存后必须能验证一致性与完整性（记录内容指纹）。
- 图片文件与记录文件放在一起，换机器或改数据目录后仍可用（即不依赖绝对路径）。

**边界条件**

| 情况 | 期望行为 |
| --- | --- |
| 单张 > 20MB | **不下载**，回执写明"第 N 张超过 20MB 未保存" |
| 单条 > 9 张 | 只存前 9 张，回执注明"超出 9 张，其余未保存" |
| 下载超时（单张 15 秒） | 标为失败，记录不回滚，回执注明"可重试" |
| 下载失败但记录已入库 | 记录保留，附件标失败；不得因为图片失败而删掉整条记录 |
| 同一张图被再次发来 | 按新记录存（可能是故意重发，不替用户判断） |
| 图片格式罕见（BMP/TIFF/HEIC） | 原样保存；能否在浏览器预览不纳入 P0 验收，但文件必须存在且可被外部程序打开 |

**验收标准**

- AC-2：发送 3 张不同图片（含 1 张 HEIC、1 张 >10MB），3 张全部落地；逐张比对内容指纹与发送时一致；用外部看图工具能打开。

---

#### FR-3 图文混合按一条记录处理

**用户故事**：作为用户，我发 3 张图配一句话，希望它们是同一条记录，而不是四条。

**需求描述**

- 一条消息 = **一条记录 + N 个附件**。不允许拆成多条记录，也不允许把附件挂到错误的记录上。
- 图片不改变记录的类型判断（类型描述的是"意图"，图片描述的是"载体"，两者独立）。
- 纯图片消息也是一条合法记录，正文允许为空。

**边界条件**

| 情况 | 期望行为 |
| --- | --- |
| 纯图片，无文字 | 一条记录，正文为空，标题用"图片 + 日期时间"占位 |
| 图文混合 | 一条记录，正文为文字，附件 N 张 |
| 文字 + 图片全部失败 | 记录保留（正文有效），回执说明图片全部失败 |

**验收标准**

- AC-3：发送 3 图 + 1 句话，记录页显示为**一条**，点开能看到 3 张图与那句话；数据库层面只有 1 条记录。

---

#### FR-4 幂等：重复投递不产生重复记录

**用户故事**：作为用户，我不希望因为网络抖动或重发，同一条内容出现两次。

**需求描述**

- 同一条平台消息被重复投递（重试、断线重连补发），必须只产生一条记录。
- 去重依据是平台消息标识，**不是内容**——两句话说的一模一样，是两条真实记录，不能合并。
- 同样的规则适用于附件：同一张图（同一平台图片标识）重复下载只保留一份。

**边界条件**

| 情况 | 期望行为 |
| --- | --- |
| 同消息重投 2 次 | 只有 1 条记录；第二次不新增，回执可省略或回"已存在" |
| 内容完全相同但消息标识不同 | 2 条记录（这是用户发了两次） |
| 附件重复投递 | 不产生重复文件，不产生重复附件记录 |

**验收标准**

- AC-4：同一条消息人工重放 3 次，记录总数为 1，附件文件数为 1。

---

#### FR-5 回执卡片

**用户故事**：作为用户，我发出消息后需要立刻知道"系统到底存了什么"，而不是猜。

**需求描述**

回执必须包含三部分，缺一不可：

1. **结果**：已记下 / 部分失败 / 失败
2. **解析成了什么**：类型 + 标题（或"未识别"）
3. **附件实况**：几张成功、几张失败、失败原因

**文案规范**

纯文字：

```text
已记下 · 待办
明天 3 点 见客户
```

纯图片：

```text
已记下 · 记录
图片 × 2（1.8MB）
（未识别内容，已原样保存）
```

部分失败：

```text
已记下 · 记录
这是今天的会议纪要
图片 2 张已存，1 张失败（超过 20MB）
```

彻底失败：

```text
未记下 · 原因
（内容仍保留在聊天里，请重发一次）
```

**硬规则**

- **回执不得撒谎。** 图片失败却回"已记下"属于数据事故，不是文案问题。
- 必须显示"解析成了什么"，让我能立刻发现判错。
- 失败必须给一句原因 + 一个可执行动作（重发）。

**验收标准**

- AC-5：构造 4 种回执场景（纯文字成功、纯图成功、部分失败、彻底失败），逐条比对文案字段齐全，无一条把失败写成成功。

---

#### FR-6 原文解析为类型/标题/时间

**用户故事**：作为用户，我希望不用选分类，系统自己猜个大概，猜错我改一个字就行。

**需求描述**

- 类型只有三种：**待办 / 日程 / 记录**。
- 解析规则（P0 故意从简）：

| 条件 | 判定 |
| --- | --- |
| 出现明确时间（"明天 3 点""周五前"） | 日程 |
| 出现动作意图（"要""得""记得""交""买"）且无明确时间 | 待办 |
| 其余（含纯图片） | 记录 |

- 标题：一句话概括，≤60 字；解析不出则取原文前 60 字；纯图片用"图片 + 日期时间"。
- 时间：能从话里推出来就填，推不出就留空（表示"待安排"）。

**关键立场**

- **判错不算缺陷。** P0 不追求分类准确率，只追求"不丢、不改、不重复"。
- 解析结果永远是**附加信息**，不允许因此改动原文。

**验收标准**

- AC-6：10 条真实消息中，≥8 条的类型与时间判断符合预期；其余 2 条只需改一个字（改类型或改时间）即可正确，无需重新录入。

---

#### FR-7 记录页：按天时间线 + 搜索

**用户故事**：作为用户，我打开一个本地页面，就能看到今天记了什么，也能搜到上个月的一条。

**需求描述**

- 单页应用，只保留一个页面「记录」。打开后默认显示**今天**，按时间倒序，可向下滚动加载历史。
- 搜索：按原文关键词匹配，输入即搜，5 秒内出结果。
- 每条展示：时间、类型、标题、正文摘要、附件缩略图（若有）。
- 页面仅在本机访问（loopback），**不开放局域网**。手机端不走网页，全部走飞书。

**边界条件**

| 情况 | 期望行为 |
| --- | --- |
| 无记录 | 显示空状态"今天还没有记录"+ 一句如何记录的提示 |
| 搜索无结果 | 显示"没有匹配的记录"，保留搜索框内容 |
| 记录很多（>1000 条） | 分页/增量加载，首屏 ≤ 2 秒 |
| 正文含超长文本 | 折叠为 3 行，可展开 |

**验收标准**

- AC-7：任意一条历史记录，用记得住的 2–3 个关键词，5 秒内出现在结果第一屏。

---

#### FR-8 记录页：看图

**用户故事**：作为用户，我点开缩略图能看清原图，且不依赖系统看图软件。

**需求描述**

- 列表显示缩略图；点击后在**浏览器内**查看原图（支持在同一页面放大、切换上下张）。
- 原图直接读取本地文件，不做二次压缩。
- 浏览器无法预览的格式（如 HEIC），提供"用系统程序打开"或"下载到本机"的兜底。

**边界条件**

| 情况 | 期望行为 |
| --- | --- |
| 图片文件丢失（误删/移动） | 显示占位"文件缺失"，不影响记录本身与其他附件 |
| 附件状态为失败 | 显示"未保存"标记，不显示破图 |
| 超大图（>10MB） | 原图按需加载，缩略图先行显示 |

**验收标准**

- AC-8：任意图片记录，点击后 2 秒内看到可辨认的原图；文件缺失时页面不崩溃且提示明确。

---

#### FR-9 记录页：单条编辑

**用户故事**：作为用户，我判错了想改，但只改判错的那个字段，不想重写整条。

**需求描述**

- 可编辑字段：**标题、类型、时间**。
- 不可编辑：**原文、附件**。界面上这两项为只读，且视觉上明确不可点。
- 每次编辑必须留痕：改了什么、从什么改成什么、什么时候改的。
- 保存后立即生效，无需刷新页面。

**边界条件**

| 情况 | 期望行为 |
| --- | --- |
| 标题清空后保存 | 拒绝，提示"标题不能为空"；保留原值 |
| 类型改为非法值 | UI 只提供三个选项，不存在非法值输入 |
| 时间格式错误 | 提示格式示例，不保存 |
| 并发修改同一条（多标签页） | 以后保存的为准，但需提示"该记录已被修改" |

**验收标准**

- AC-9：改类型、改标题、改时间各一次，三次改动均在变更记录中可查；原文与附件无任何变化（比对指纹）。

---

#### FR-10 软删除与恢复

**用户故事**：作为用户，我误删了一条，希望一周内还能找回来。

**需求描述**

- 删除为**软删除**：记录从列表消失，进入回收站，保留 7 天。
- 恢复时连同附件一起恢复（附件文件在保留期内不移动、不删除）。
- 7 天后由清理动作彻底删除；P0 只提供手动清理命令，**不做定时任务**。

**边界条件**

| 情况 | 期望行为 |
| --- | --- |
| 删除含图片的记录 | 记录与附件一起进回收站；文件保留在原位 |
| 7 天内恢复 | 记录与附件全部回来，时间戳不变 |
| 超过 7 天未恢复 | 手动清理时删除记录与物理文件 |
| 恢复后再次删除 | 重新计算 7 天 |

**验收标准**

- AC-10：删除 → 恢复 → 再删除，三步中数据与附件始终一致；恢复后图片仍能打开。

---

#### FR-11 Markdown 导出

**用户故事**：作为用户，我希望即使这个工具不在了，我的数据也能被任何编辑器打开。

**需求描述**

- 导出为按天分文件的 Markdown，一天一个文件，文件名用日期。
- 正文为原文（不做改写），图片以相对路径引用，导出目录自带附件副本。
- 导出内容必须能被我手写的内容区分：只导出事实，不添加任何评价、总结、标签。

**边界条件**

| 情况 | 期望行为 |
| --- | --- |
| 部分附件失败 | 导出中标注"（图片未保存）" |
| 纯图片记录 | 导出为图片 + 占位标题 |
| 中文/表情/换行 | 保持原样，UTF-8 编码，LF 换行 |

**验收标准**

- AC-11：导出一个月的记录，用任意编辑器（记事本、VS Code、Typora）打开均不乱码、图片能显示。

---

#### FR-12 三平台可启动

**用户故事**：作为用户，我换到 Linux 或 macOS 上也要能跑，而不是"只有 Windows 能用"。

**需求描述**

- Windows 10/11、Linux、macOS **同等支持**，不接受"先 Windows，后面再适配"。
- 三平台只在"从系统取东西"的地方不同（数据目录、路径、编码、时区），业务逻辑完全共用。
- 数据目录优先读环境变量；未设置时按平台规范存放，**禁止写入程序所在目录**。
- 不做系统通知、托盘、剪贴板、文件监听，也不调用系统看图程序——提醒走飞书卡片，看图走浏览器。这一条同时是最省事的跨平台方案。

**验收标准**

- AC-12：同一份代码在 Windows 与一个 POSIX 环境（Linux 或 macOS）各启动一次，均能建库、能收文字、能收图片、能在浏览器看记录。
- 出现第一处平台判断分支时，必须在技术约束文档中登记原因。

---

## 5. 信息需求（数据要能表达什么）

不规定表名与字段类型，只规定**必须能被表达与查询的信息**：

| 信息 | 必要性 | 说明 |
| --- | --- | --- |
| 原始正文 | 必须 | 只写一次，永不改写。纯图片记录允许为空 |
| 类型 | 必须 | 待办 / 日程 / 记录，三选一 |
| 标题 | 必须 | ≤60 字，非空 |
| 时间 | 可选 | 空 = 待安排 |
| 状态 | 必须 | P0 只有"有效 / 已删除"两种，不做完成流转 |
| 来源 | 必须 | 飞书 / 本地 |
| 来源消息标识 | 必须 | 用于幂等，**必须唯一** |
| 创建时间 | 必须 | 本地时区 |
| 附件集合 | 可选 | 0..N，每个附件含：相对路径、格式、字节数、内容指纹、来源图片标识（唯一）、下载状态 |
| 变更记录 | 必须 | 每次编辑：哪条、哪个字段、原值、新值、时间、来源 |

**三条信息层约束（比字段更重要）**

1. **原文与附件字节不可变**：任何"加工"只能写进新字段，不能覆盖事实。
2. **路径只存相对形式**：绝对路径在运行时由数据目录拼接，保证换机器可用。
3. **不预建未来才用的结构**：P1/P2 需要的"每天""计划""整理"相关数据，P0 不建。日期是可派生的视图，不是存储。

## 6. 业务规则（不随实现变化的判定）

| # | 规则 | 违反了会怎样 |
| --- | --- | --- |
| R1 | 先存原文，再解析 | 解析一挂，数据就丢，这是最不可接受的失败 |
| R2 | 原文与图片字节不可改写 | 存的不再是"我说的话"，整个产品的证据基础崩掉 |
| R3 | 幂等靠平台消息标识，不靠内容 | 靠内容会误合并真实重复记录 |
| R4 | 附件失败不回滚记录 | 因为一张图失败丢掉整条消息，等于放大损失 |
| R5 | 回执必须如实反映实况 | 撒谎比缺功能更糟，会让我误以为数据安全了 |
| R6 | 删除是软删除，7 天内可恢复 | 单用户本地工具，误删不可恢复是不可接受的 |
| R7 | 手机侧只走飞书，网页只监听本机 | 为"手机也能开网页"引入鉴权与端口暴露，不是 MVP 该付的成本 |

## 7. 非功能需求

| 类别 | 要求 |
| --- | --- |
| **性能** | 纯文字回执 ≤ 5 秒（P95）；含图片 ≤ 15 秒/张；记录页首屏 ≤ 2 秒（1000 条内）；搜索 ≤ 5 秒 |
| **可靠性** | 进程异常退出后重启，已入库数据不丢；未完成的消息在重启后可被识别并补处理 |
| **可用性** | 断网时记录查看、搜索、编辑、导出必须可用（飞书收发除外） |
| **隐私** | 全部数据留在本机；除飞书官方接口外不发往任何第三方；解析用的模型调用不得携带附件原图以外的额外上下文 |
| **可移植** | 数据目录可整体搬移；换机器后记录与图片均可用 |
| **可观测** | 每次失败至少有一处人可见的痕迹（回执或页面提示），日志仅作辅助 |
| **资源占用** | 常驻进程空载内存 < 200MB；附件目录增长可见（提供查看总占用） |

## 8. 验收矩阵

验收只有两种结果：**通过 / 不通过**。不设"基本可用"。

| 编号 | 验收项 | 验收方式 | 通过标准 | 关联需求 | 周次 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| AC-1 | 文字不丢不改 | 连发 10 条，逐字比对 | 10/10 一致 | FR-1 | W1 | 未实现 |
| AC-2 | 图片原样 | 发 3 图（含 HEIC、>10MB），比对指纹 | 3/3 一致且可外部打开 | FR-2 | W1 | 未实现 |
| AC-3 | 图文一条 | 发 3 图 + 1 句 | 记录数为 1，附件为 3 | FR-3 | W1 | 未实现 |
| AC-4 | 幂等 | 同消息重放 3 次 | 记录 1 条，附件 1 份 | FR-4 | W1 | 未实现 |
| AC-5 | 回执如实 | 构造 4 种场景核对文案 | 无一条把失败写成功 | FR-5 | W1 | 未实现 |
| AC-6 | 解析可用 | 10 条真实消息 | ≥8 条正确，其余改一字可修 | FR-6 | W2 | 未实现 |
| AC-7 | 搜得到 | 任取 5 条历史记录 | 5/5 在 5 秒内命中首屏 | FR-7 | W3 | 未实现 |
| AC-8 | 看得到图 | 点开 3 条含图记录 | 2 秒内可辨认；缺失有提示不崩 | FR-8 | W3 | 未实现 |
| AC-9 | 可修正 | 改类型/标题/时间各一次 | 均生效且留痕，原文未变 | FR-9 | W3 | 未实现 |
| AC-10 | 可恢复 | 删→恢复→再删 | 数据与附件始终一致 | FR-10 | W4 | 未实现 |
| AC-11 | 可导出 | 导出一月记录，3 种编辑器打开 | 不乱码，图片可显示 | FR-11 | W4 | 未实现 |
| AC-12 | 跨平台 | Win + 一个 POSIX 各启动一次 | 建库、收文字、收图片、看记录全通 | FR-12 | W1 起 | 未实现 |

**全局验收（两周连续使用后判定，七条同时成立）**

1. 每天 ≥5 条，连续 14 天，无一条丢失。
2. 无一条重复。
3. 无一条原文被改写（逐条比对）。
4. 每张图与发送时字节一致。
5. 回执时延达标。
6. 任意历史记录 5 秒内搜到。
7. 全过程不需要手动整理、分类、填写表单。

## 9. 里程碑

每周只交付一个动作。**任一周验收不过，不进入下一周。**

| 周 | 主题 | 交付 | 周末唯一验收 |
| --- | --- | --- | --- |
| W1 | 收得下 | 文字与图片都能落库并回执 | 连记 10 条（含 3 条纯图、2 条图文）全在，文字一字不差、图片能打开 |
| W2 | 记得准 | 文字解析类型/标题/时间；图片元数据与下载状态齐全 | 10 条里 ≥8 条类型与时间正确 |
| W3 | 取得回 | 记录页：时间线 + 搜索 + 看图 + 改一个字 | 任意一条（含图片）5 秒内找到并改掉 |
| W4 | 存得住 | 软删除与恢复、Markdown 导出、三平台冒烟 | 删后 7 天内可恢复（含附件）；导出任意编辑器可开 |

**跨平台要求贯穿全程**：W1 结束前必须完成一次双平台启动；此后每引入"从系统取东西"的能力，当周验收补一条跨平台检查。

## 10. 风险与依赖

### 10.1 风险

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 图片拖慢核心验证 | 忙着做预览、压缩、OCR，却还没验证"能不能存住" | P0 图片只做"原样存 + 能打开"；压缩与识别推 P1 |
| 回执撒谎 | 图片失败但回执说"已记下" | 回执逐张汇报；失败必须在卡片出现，且记录不回滚 |
| 原文被加工 | 回执好看，但存的是"润色后的话" | 原文只读、只写一次；任何改写视为数据事故 |
| 路径不可移植 | 数据里写死绝对路径，换机器全部失效 | 只存相对路径，绝对路径运行时拼 |
| 只在 Windows 验证 | 适配成本推迟到以后，最终一项都跑不起来 | 每周验收带一次跨平台启动 |
| 范围回潮 | 又想加新闻、健康、文件管理 | 用 §2.2 挡回去：不影响"能不能记进去"的一律不做 |
| 解析追求准确率 | 为了 90% 分类准确率引入复杂模型，拖慢记录链路 | 明确"判错不算缺陷"，解析失败不阻塞入库 |

### 10.2 依赖

| 依赖 | 说明 | 缺失时的影响 |
| --- | --- | --- |
| 飞书自建应用凭据（App ID / Secret） | 收消息、发回执、下载图片的必要条件 | 无法接入真实通道；W1 可在本地模拟消息完成入库与回执验证，但 AC-1/AC-2 不算通过 |
| 图片下载接口的可访问性 | 部分网络环境需代理 | 图片全部失败，回执必须明确报出，不得静默 |
| 解析所用模型的可用性 | 用于类型/标题/时间 | 解析降级为默认值，入库不受影响（R1） |
