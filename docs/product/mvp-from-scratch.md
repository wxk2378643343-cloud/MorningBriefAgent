## 0. 为什么先做记录

想做的三件事里，只有一件是不可替代的地基：

```text
记录（数据在）  →  计划（今天做什么）  →  整理（这一天是什么样）
   必须最先做         依赖记录质量          依赖记录完整度
```

没有连续、可信的记录，后面两步都是拿残缺数据编故事：计划会排给一个不存在的"我"，整理会写出与事实不符的段落。

所以 P0 的验收标准只有一条：**我说过的话、发过的图，都能在本地被完整、准确地找回来。**

## 1. 产品愿景（不变）

> 一个只做一件事的私人助理：**每天早上告诉你今天该做哪几件事，晚上把这一天写成一段记录。**

愿景分三期兑现，P0 只交付第一期。

| 期 | 交付 | 状态 |
| --- | --- | --- |
| **P0** | 记录层：文字与图片 → 原样存下 → 随时取回 | **当前唯一目标** |
| P1 | 计划层：早上给出当天该做的事（件数由承载量推导） | 等 P0 验收通过 |
| P2 | 整理层：把当天记录原样整理成一段文字 | 等 P1 稳定 |

**"复盘"这个词从本规格中移除。** 它暗示评价、打分、建议，而产品只做记录与回放。P2 只做「整理」：把当天发生的事按时间顺序陈述一遍，不做判断。

## 2. P0 定义：把数据可靠地记进去

### 2.1 四条硬规则

这四条是 P0 的全部技术主张，任何实现都必须满足：

| # | 规则 | 含义 |
| --- | --- | --- |
| 1 | **先存原文，再解析** | 收到消息立刻落原文，解析失败也不丢数据。解析是附加层，可以重跑 |
| 2 | **原文与图片不可改写** | 模型只能产出"结构化字段"，永不允许改写 `raw_text`，也不允许压缩、裁切、转格式 |
| 3 | **幂等** | 同一条消息重复投递只产生一条记录；同一张图重复下载只产生一条附件。以平台 `message_id` 与 `image_key` 去重 |
| 4 | **失败可见** | 存失败、图片下载失败、解析失败都必须回卡说明，不允许只在日志里 |

规则 1 和 2 是这套设计区别于"聊天记录导出"的地方：**结构化是装饰，原始文字与原始图片是事实。**

### 2.2 一条记录包含什么

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `raw_text` | 用户原话 / 图片 caption | 不可变，一字不改。纯图片消息允许为空字符串 |
| `kind` | 解析得出 | `task` / `event` / `note`，只有这三种 |
| `title` | 解析得出 | 一句话概括，最长 60 字；解析不出就用原文前 60 字；纯图片用"图片 2026-11-05 14:16" |
| `due_at` | 解析得出 | 可为空。空 = 待安排 |
| `status` | 系统 | P0 一律 `open`，不做完成流转 |
| `source` | 系统 | `feishu` / `local` |
| `source_message_id` | 平台 | 幂等键，唯一索引 |
| `created_at` | 系统 | 本地时区 |
| `attachments` | 系统 | 0..N 张图，见 2.4 |

**`kind` 描述意图，附件描述载体。** 图片不新增 `kind`——"拍了张白板"仍然是 `note`，"明天带着这张图去见客户"是 `task`。两者正交，查询时用 `attachments` 是否为空来筛图片记录。

**判定规则（P0 故意从简）**：

- 出现明确时间（"明天 3 点""周五前"）→ `event`
- 出现动作意图（"要""得""记得""交""买"）且无时间 → `task`
- 其余 → `note`（纯图片消息默认 `note`）
- **判错不算 bug**，我改一个字就行。P0 不追求分类准确率，只追求"不丢、不改、不重复"

### 2.3 三种消息形态都必须支持

| 形态 | 示例 | P0 处理 |
| --- | --- | --- |
| 纯文字 | "明天 3 点见客户" | 原文 + 解析字段 |
| 纯图片 | 一张白板照片，无文字 | `raw_text` 为空，附件 1 张，`title` 用占位 |
| 图文混合 | 3 张图 + "这是今天的会议纪要" | 文字与 3 张附件挂在同一条记录上 |

**混合消息是一等公民，不是拼接出来的两次记录。** 一条消息 = 一条 `items` + N 条 `attachments`。

### 2.4 图片处理规则

| 事项 | 规则 |
| --- | --- |
| **原样保存** | 存原始字节，不压缩、不裁剪、不转格式。HEIC 也原样存，P0 不做转换 |
| **存储位置** | `DATA_DIR/attachments/YYYY/MM/DD/<item_id>/<序号>_<sha8>.<ext>`，全部 `pathlib` 拼接 |
| **文件名** | 只用 ASCII 与数字，禁止中文、空格、冒号等跨平台敏感字符 |
| **元数据** | 记录 `mime`、`bytes`、`sha256`、原始文件名（如有）、`image_key`、下载状态 |
| **上限** | 单张 ≤ 20MB；单条消息 ≤ 9 张。超限的图不下载，回执里明确写出"第 3 张超过 20MB 未保存" |
| **下载超时** | 单张 15 秒。超时标记 `failed`，记录照常入库，回执注明可重试 |
| **不做 OCR** | P0 不识别图片里的文字。图片先"存得住"，识别属于 P1 解析增强 |
| **不做跨消息去重** | 同一张图被再次发来，按新记录存。可能是故意重发，P0 不替用户判断 |

**附件与文字互不阻塞**：文字先入库，图片下载失败不回滚记录。宁可留下"1 张图待重试"，也不能让一条消息因为图片挂了而消失。

### 2.5 回执

每条记录成功后立即回一张卡片。**回执必须如实反映实际存下了什么**，不能因为"应该成功"就说成功。

纯文字：

```text
已记下 · 待办
明天 3 点 见客户
（没识别到时间）
```

纯图片：

```text
已记下 · 记录
图片 × 2（1.8MB）
（未识别内容，已原样保存）
```

图文混合且部分失败：

```text
已记下 · 记录
这是今天的会议纪要
图片 × 2 已存，1 张失败（超过 20MB）
```

- 纯文字回执 ≤ 5 秒（P95）；含图片 ≤ 15 秒 × 张数上限内可控，若超时则先回执并写明"图片待重试"。
- 回执必须显示"解析成了什么"和"存了几张图"，让我能立刻发现判错。
- 存失败时回执改为红卡 + 一句原因 + 「重发一次」提示。**不允许静默失败。**

## 3. P0 数据模型

三张表。P0 不需要"每天"这个概念——日期是可从 `items` 派生的视图，不是存储。

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `items` | 一条消息 = 一条记录 | `id`、`raw_text`、`kind`、`title`、`due_at`、`status`、`source`、`source_message_id`(唯一)、`created_at`、`deleted_at` |
| `attachments` | 图片附件，1 条记录 N 张 | `id`、`item_id`、`rel_path`、`mime`、`bytes`、`sha256`、`image_key`(唯一)、`status`(ready/failed)、`created_at` |
| `changes` | 变更流水 | `item_id`、`field`、`from`、`to`、`at`、`by` |

约束：

- `items.source_message_id` 与 `attachments.image_key` 均建唯一索引，幂等靠数据库兜底，不靠应用层判断。
- 附件只存相对路径 `rel_path`，绝对路径由 `DATA_DIR` 在运行时拼——数据库搬到另一台机器仍可用。
- 删除是软删除（`items.deleted_at`），7 天内可恢复；恢复时连同附件一起恢复。
- 物理文件在软删除期间**不移动**，7 天后由清理任务删除（P0 只实现清理命令，不做定时）。
- 时间一律存本地时区，展示不做二次转换。
- **不预建** `days`、`plans`、`reviews` 表。P1 再加。

## 4. P0 界面：只有一页

| 页面 | 用途 | 形态 |
| --- | --- | --- |
| **记录** | 按天看时间线、搜索、看大图、改一个字、删除、恢复 | 本地网页，仅监听 `127.0.0.1` |

没有"今天"页，没有"回顾"页——P0 没有计划和整理，做了也是空的。

页面必备五件事：

1. 默认显示今天，按时间倒序，能往下翻历史
2. 搜索框（按原文关键词，5 秒内出结果）
3. 图片以缩略图显示，点击在浏览器内看原图（走本地 `/api/attachments/{id}`，不调用系统看图程序，避免跨平台差异）
4. 单条可编辑（只允许改标题、类型、时间；`raw_text` 与附件只读）
5. 删除进回收站，7 天内可恢复

**手机不走网页。** 手机上的全部操作由飞书卡片完成。网页只监听 loopback，不开放局域网访问。

## 5. 明确不做

P0 阶段连提都不要提的：

- 早间计划、件数计算、承载量公式（P1）
- 每日整理、周报月报、任何形式的"复盘"或评价（P2）
- OCR、图片内容识别、图片相似去重（P1 解析增强）
- 图片压缩、缩略图预生成、EXIF 清理（P0 只做"能看"，不做"优化"）
- 完成状态流转、顺延天数、拖延统计（P1）
- 新闻、行情、基金、健身、饮食、微信聊天分析
- 知识库文件管理、文件夹同步、文件恢复
- 数据库浏览器、工作流调度中心、Agent 运行监控
- 多用户、账号、权限、云同步、移动 App、Web 公网版
- 图表、统计报表、打卡连续天数
- 插件体系、Provider 市场、多渠道（除飞书外）

理由统一为一句：**不影响"我能不能把文字和图片完整记进去"的，一律不做。**

### 存量能力的处置（已确认：全部下线）

- 产品层面不投入，也不保留入口。
- 旧实现不作为新基础。需要某个能力时按新规格重写，不做代码移植。
- 旧数据不迁移、不兼容。P0 使用独立数据库文件与独立附件目录，避免与历史运行数据互相污染。

## 6. 技术与运行约束

- **本地优先**：断网时记录与查询必须可用（飞书推送除外）。
- **一个常驻进程**：同时提供本地 HTTP（只监听 127.0.0.1）与飞书长连接。
- **调度不依赖操作系统**：P0 无定时任务。P1 引入时由进程内调度 + 启动补跑实现。
- **前端不引入构建链**：静态 HTML + 原生 `fetch`，不引入 npm/Vite/React。
- **Agent 只在一个地方用**：把原文解析成结构化字段。解析失败不影响入库，纯图片消息可以不调用 Agent。
- **可恢复**：软删除 7 天，回收站可查可还原，附件一并恢复。

### 6.1 跨平台差异的处理规则

Windows 10/11、Linux、macOS **同等支持**，不接受"先 Windows 后面再适配"。三平台只在"从系统拿东西"的地方不同，其余逻辑必须完全共用。

| 事项 | 规则 |
| --- | --- |
| **数据目录** | 优先读环境变量 `DATA_DIR`；未设置时按平台规范：Windows `%APPDATA%`、macOS `~/Library/Application Support`、Linux `$XDG_DATA_HOME`（缺省 `~/.local/share`）。**不使用相对路径，不写入程序所在目录** |
| **路径处理** | 一律 `pathlib`，不手工拼接分隔符；文件名只用 ASCII 与数字；不假设大小写敏感或不敏感 |
| **编码** | 文本读写显式 `encoding="utf-8"`，Markdown 统一 `\n` 换行；**图片一律以二进制读写**，禁止经过文本编码 |
| **时区** | 全部用本机本地时区；"今天"取 `[00:00, 次日 00:00)` 半开区间 |
| **调度** | P0 无定时任务。P1 引入时：进程内休眠 + 启动补跑（已过 07:00 未生成计划则补，12:00 后只补"下午剩余"并标注「补生成」） |
| **进程常驻** | 只提供前台运行命令，不写自启脚本。文档给出三平台自启写法作为可选项，不进验收 |
| **系统集成** | 不做系统通知、托盘、剪贴板、文件监听，也不调用系统看图程序。提醒走飞书卡片，看图走浏览器 |

## 7. P0 路线（四周，只围绕"记录"）

| 周 | 目标 | 周末验收（唯一标准） |
| --- | --- | --- |
| W1 | 收得下：文字与图片都能落库并回执 | 连记 10 条（含 3 条纯图、2 条图文），10 条都在，**文字一字不差、图片能打开** |
| W2 | 记得准：文字解析类型/时间/标题；图片记录元数据与下载状态 | 10 条里 ≥ 8 条类型与时间正确；每张图 mime/大小/哈希齐全 |
| W3 | 取得回：本地「记录」页，时间线 + 搜索 + 缩略图 + 编辑 | 任意一条（含图片）能在 5 秒内找到并改掉 |
| W4 | 存得住：软删除与恢复、Markdown 导出、三平台冒烟 | 删除后 7 天内可恢复（含附件）；导出能被任意编辑器打开 |

**跨平台验收（贯穿）**：

- W1 结束前，同一份代码必须在 Windows 与一个 POSIX 环境（Linux 或 macOS）各启动一次，能建库、能收文字与图片。
- 每当引入"从系统取东西"的代码（路径、时间、进程、编码、文件读写），必须在该周验收补一条跨平台检查。
- 出现第一处 `if sys.platform ==` 分支时，要在 6.1 记录原因；不允许平台判断散落在业务代码里。

每周只交付一个动作。任一周验收不过，不进入下一周。

## 8. P0 成功标准

连续使用两周后判定，七条同时成立：

1. 每天记录 ≥ 5 条，连续 14 天，**无一条丢失**（文字与图片都算）。
2. 无一条重复（同一消息被记两次即为失败）。
3. 无一条原文被改写（逐条比对发送内容）。
4. 每张图都能打开，且与发送时的原图**字节一致**（比对 sha256）。
5. 记录到回执：纯文字 ≤ 5 秒；含图片 ≤ 15 秒/张。
6. 任意历史记录能在 5 秒内搜到。
7. 全过程不需要手动整理、分类、填写表单。

有一条不中，问题在记录层，不在功能数量。

## 9. P1 / P2 已定事项（暂不实施，防止丢失）

**P1 早间计划**

- 件数由承载量推导，范围 1–5，默认 3：`可用时长 = 清醒时段 - 日程占用 - 生活缓冲(4h)`；`基础件数 = 可用时长 / 90 分钟`；昨天完成率 < 50% 则 -1。
- 日程不占条数但吃时长；卡片第一行必须写明件数理由。
- 验收含"10 天里件数不能永远是 3"。

**P1 解析增强**

- 图片 OCR：把图里的文字作为**附加字段**，不改 `raw_text`，不覆盖原图。

**P2 整理（不是复盘）**

- 只陈述事实与顺序，不做评价、不打分、不给建议。
- 硬限 150 字；输出同时落成本地 Markdown。
- 用户只读；发现记错可在次日说一句让系统改。

## 10. 最大的风险

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 图片把记录层拖慢 | 忙着做图片预览、压缩、OCR，却还没验证"能不能存住" | P0 图片只做"原样存 + 能打开"，压缩与识别一律推到 P1 |
| 回执撒谎 | 图片下载失败但回执说"已记下" | 回执逐张汇报状态；失败必须在卡片上出现，且记录不回滚 |
| 附件路径不可移植 | 数据库写死绝对路径，换机器或改 `DATA_DIR` 后全部失效 | 只存 `rel_path`，绝对路径运行时拼 |
| 原文被模型加工 | 回执好看，但存的是"润色后的话" | `raw_text` 只读、只写一次；任何改写视为数据事故 |
| 只在 Windows 上验证 | 适配成本推迟到以后，最终一项都跑不起来 | 每周验收带一次跨平台启动 |
| 范围回潮 | 又想加新闻、健康、文件管理 | 用第 5 节挡回去：不影响"能不能记进去"的，一律不做 |
