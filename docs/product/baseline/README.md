# 基线目录（baseline）

存放 **已冻结的需求基线快照**。这里的东西是"当时到底定了什么"的唯一证据，用来在几周或几个月后回答：这个决定是哪一版定的、后来为什么改、改之前长什么样。

## 目录约定

```
docs/product/baseline/
├── README.md                                  ← 本文件：规则 + 登记表
├── BL-001-PRD-2026-001-v2.3.md                ← 冻结快照（只读，永不修改）
├── BL-001-record.md                           ← 基线记录（身份、假设、未决项、变更登记）
└── BL-002-...                                 ← 下一个基线，同样成对出现
```

**快照与记录必须成对存在。** 只有快照没有记录，复盘时不知道当时在想什么；只有记录没有快照，无法验证是否被改过。

## 三条硬规则

1. **快照只读。** 任何情况下不修改已冻结的快照文件。发现错别字也不改——改了就失去"当时原文"的意义，错别字恰恰是复盘素材。
2. **正文继续演进。** 基线之后，`prd.md` 继续原地迭代并升版本号，快照留作对照。两者 diff 就是这一段时间的决策轨迹。
3. **改已冻结条款，先登记再改。** 在 `BL-xxx-record.md` 第 6 节「变更登记」追加一行，写清类型、涉及条款、原因、影响分析。未登记就改正文 = 流程违规。

## 命名规则

| 类型 | 格式 | 示例 |
| --- | --- | --- |
| 快照 | `BL-<三位序号>-<文档编号>-<版本号>.md` | `BL-001-PRD-2026-001-v2.3.md` |
| 记录 | `BL-<三位序号>-record.md` | `BL-001-record.md` |
| Git 标签 | `baseline/BL-<三位序号>` | `baseline/BL-001` |

序号全局递增，不复用。作废的基线保留，不删——作废本身也是决策记录。

## 什么时候打基线

| 触发 | 必须打 |
| --- | --- |
| 首次进入开发（G1 通过） | ✅ 初版基线 |
| 需求增删或验收口径变更并被确认 | ✅ 新基线（BL-002 起） |
| 方向推翻、产品定位改变 | ✅ 新文档 + 新基线 |
| 只改错别字、排版、示例 | ❌ 不升版本、不打基线 |

## 怎么打一个新基线（BL-002 及以后）

```bash
# 1. 确认当前正文已是"确认过的状态"，版本号已升
grep -n "当前版本" docs/product/prd.md

# 2. 冻结快照（只复制，不改内容）
cp docs/product/prd.md docs/product/baseline/BL-002-PRD-2026-001-v2.4.md

# 3. 记下校验值，填入新记录文件
sha256sum docs/product/baseline/BL-002-PRD-2026-001-v2.4.md

# 4. 复制上一份记录做模板，改身份信息，变更登记表从空白开始
cp docs/product/baseline/BL-001-record.md docs/product/baseline/BL-002-record.md

# 5. 提交并打标签
git add docs/product/baseline && git commit -m "docs(prd): 冻结基线 BL-002 (v2.4)"
git tag -a baseline/BL-002 -m "PRD-2026-001 v2.4 基线"
```

第 4 步的模板复制不是形式主义：**「可被证伪的关键假设」这一节必须逐条重写**，因为旧假设可能已被证伪，新版本要写新的赌注。

## 怎么用它做复盘

复盘不是回忆，是比对。三种用法：

**1. 看决策轨迹**

```bash
diff docs/product/baseline/BL-001-PRD-2026-001-v2.3.md docs/product/prd.md
```

差异集中在哪几节，哪几节就是这段时间真正被现实推动过的地方。从来没被改过的章节，要么特别稳，要么根本没人看——两种结论都值得记下来。

**2. 验证假设**

打开 `BL-xxx-record.md` 第 3 节，逐条问"这条成立了吗"。每条都写了「若被证伪的后果」，所以证伪之后返工范围是现成的，不用重新分析。

**3. 统计返工来源**

看变更登记表的「变更类型」列。如果 `验收口径变更` 出现最多，说明验收当初写得不可判定；如果 `需求增删` 最多，说明需求收集阶段没问够。**这个统计直接决定下一轮该在哪个环节多花时间。**
