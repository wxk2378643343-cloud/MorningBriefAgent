## 1. 产品定义

### 1.1 一句话

> 把你飞书里散着的任务和日程正确展示出来，再根据已有日程、任务和历史完成情况，每天早上排成能做完的一天；晚上告诉你今天实际完成了什么，后续用数据复盘。

### 1.2 四条原始需求

| # | 原话 | 产品含义 |
| --- | --- | --- |
| N1 | 用飞书的任务和日程帮我制定任务和计划 | 飞书是**任务与日程事实源 + 操作面板**；一期必须正确展示两类数据 |
| N2 | 每天根据任务和完成了什么做记录，然后推荐第二天 | 完成由用户在飞书标记；系统同步完成状态并沉淀复盘数据 |
| N3 | 我要给他我是什么角色，然后进行任务规划 | 规划必须因人而异，角色要**参与计算** |
| N4 | 可以考虑调用多个 AI 平台 | 一期支持切换 API；模型是可替换零件，不改变产品流程 |

### 1.3 核心闭环

```text
同步任务/日程 → 生成今日计划和日程建议 → 回复"可以" → 写回任务和日程
       ↑                                      ↓
       └──── 用户在飞书标记完成 ←── 同步完成状态
                         ↓
                     复盘数据
```

| 时间（默认可配） | 系统做什么 | 你要做什么 |
| --- | --- | --- |
| 07:00 | 同步任务与日程，展示今日已有日程、可用时间和计划建议 | 回复"可以"或后续修改 |
| 全天 | 同步任务状态和完成情况 | 在飞书标记任务完成 |
| 21:30 | 根据计划与完成状态生成基础复盘数据 | 查看复盘结果 |
| 次日 07:00 | 使用历史计划、日程和完成数据生成新计划 | 回复"可以"采纳 |

**一期闭环验收**：页面正确展示飞书任务和日程；AI 根据真实可用时间生成任务和日程建议；用户回复"可以"后任务和日程写回飞书；用户在飞书标记任务完成后，页面能同步并形成复盘数据。

## 2. 业务流程

### 2.1 一天的主线

| 阶段 | 触发 | 系统做什么 | 你做什么 | 异常分支 |
| --- | --- | --- | --- | --- |
| **P0 数据同步** | 打开页面、生成计划、生成复盘、用户主动刷新；收到飞书事件时即时更新 | 按需拉取飞书任务/日程 → 更新本地镜像并记录差异；生成复盘前可执行一次全量拉取 | 无 | 拉取失败 → 保留上次成功数据并明确提示；不得把未拉到误判为已删除 |
| **P1 出计划** | 07:00（可配） | 根据任务、已有日程、历史计划和完成数据，计算可用时间 → 模型选择任务并写理由 → 出计划卡 | 回"可以"采纳 / "改：…" 调整 | ① 模型全挂 → 出裸排序并标注；② 无任何任务 → 询问是否新增任务；③ **你不回 → 不写回飞书**，12:00 提醒一次，随时回"可以"可补写 |
| **P2 执行** | 用户在飞书勾选完成后；或用户打开页面/发起对话时 | 优先接收飞书任务变更事件并更新本地；事件不可用或漏事件时按需重新拉取；处理随手记与对话完成 | 在飞书勾完成 | 事件订阅不可用 → 以按需拉取为准；同步失败保留上次状态并提示 |
| **P3 出记录** | 21:30（可配） | 从账本算事实（完成项、顺延天数、日程占用）→ 模型写成话 → 出草稿卡 | 回"对"落档 / "改：…" 更正后落档 | ① 0 完成 → 仍生成，写"今日无完成项"并列原因候选，不给结论；② **不回 → 22:30 自动落档并标"未确认"**，次日可补正 |
| **P4 建议回流** | 次日计划生成时；按用户选择的跟踪模式 | 按"日跟踪"或"周跟踪"生成建议：日跟踪关注昨日计划，周跟踪关注本周重复工作、周期任务和连续未完成事项 | 选择跟踪模式，可随时切换 | 建议连续被忽略 → 降低优先级并询问是否继续跟踪，不直接永久删除 |

### 2.2 三条支流程

**A 随手记（一句话 → 任务/日程/记录）**

```text
收到消息 → 判定 kind（任务/日程/补充/纯记录）+ 解析时间
        → 与本地未完成任务查重
        → 回确认卡（判定结果 + 拟创建内容 + 查重结果）
        → 你回"行" → 写飞书 → 落本地 → 回执
         你回"改：…" → 按更正重出卡
         你不回 → 不创建，卡保留 24 小时后失效
```

**B 对话完成（"X 完成了"）**

| 匹配结果 | 处理 |
| --- | --- |
| 唯一命中 | 直接 PATCH 飞书 `completed_at` → 成功后随同步回流本地 |
| 多个候选 | 回"是指哪个？1… 2…"，你选号后才写 |
| 零命中 | 回"没找到这条，是要新建并标记完成吗？"，**不自动创建** |

写失败（网络/权限）→ 任务保持未完成，回执说明原因。系统**永不自主勾完成**，一期由用户在飞书手动标记完成。

**C 历史回灌与对账**

| 动作 | 时机 | 做什么 | 关键约束 |
| --- | --- | --- | --- |
| 回灌 | 首次接入、手动重跑 | 翻页拉全部已完成任务（`completed=true`）→ 落本地标 `backfilled` | 只用于统计与推荐，**不进今日候选**；已删除的拉不到，缺的就是缺的 |
| 增量对账 | 每次同步顺带 | 核对本次涉及条目 | 成本近零 |
| 全量对账 | 每日一次（记录生成前） | 全库比对，产出偏差清单 | **只出清单，不自动修复** |

### 2.3 状态机

**任务镜像（本地）**

| 状态 | 含义 | 如何流转 |
| --- | --- | --- |
| `synced` | 与飞书一致 | 同步 → 覆盖字段并写流水 |
| `pending_create` | 已确认，尚未写成功 | 写成功 → `synced`；失败退避重试，3 次告警 |
| `pending_update` | 本地有改动待写 | 同上；此期间同字段不被同步覆盖（FR-18） |
| `deleted_in_feishu` | 飞书已删（有 ID 但查不到） | 保留历史；不进候选、不计完成 |
| `backfilled` | 历史回灌数据 | 只读，仅用于统计 |

**计划**

| 状态 | 含义 | 流转 |
| --- | --- | --- |
| `draft` | 已生成，未确认 | 12:00 前未确认则保持本地生效、不写飞书 |
| `confirmed` | 你回"行" | 触发写飞书 |
| `partial` | 部分事项写失败 | 失败项回落 `pending_create` 重试 |

**记录**

| 状态 | 含义 | 流转 |
| --- | --- | --- |
| `draft` | 草稿待确认 | 回"对"→ `confirmed`；回"改：…"→ 修订后落档并保留原稿 |
| `confirmed` | 已落档 | 不可编辑；更正走次日补记 |
| `auto_archived` | 超时自动落档，标"未确认" | 次日可补正 |

### 2.4 写飞书的统一时序

所有"要改飞书"的动作走同一套，不单独实现：

```text
1. 本地先记 pending（写什么、为什么、何时）
2. 调飞书接口（创建带 client_token 幂等；更新按飞书 ID 定向）
3. 成功 → 回填飞书 ID → 本地转 synced
4. 失败 → 保持 pending，回执写明原因，退避重试（1/5/15 分钟，3 次后告警）
5. 飞书没成功，本地绝不先改成成功态
```

## 3. 数据归属与同步

### 3.1 谁说了算

| 数据类别 | 例子 | 事实源 | 谁写 | 冲突规则 |
| --- | --- | --- | --- | --- |
| **当前态** | 任务是否存在、标题、截止、优先级、**是否完成** | **飞书** | 系统确认后写；你也可在飞书手改 | 飞书覆盖本地，覆盖前把旧值写一条流水 |
| **历史态** | 几时完成的、改过几次截止、被顺延几次、哪天进的计划 | **本地** | 系统写，只追加 | 永不被覆盖 |
| **生成物** | 每日计划、每日记录、推荐、模型调用记录 | **本地** | 系统写 | 记录落档后不可改 |
| **配置** | 角色档案、模型池 | **本地** | 你改 | 带版本号，改动可追溯 |

**读操作一律只读本地**（计划、记录、推荐、检索），飞书只在同步时被碰。这不只是性能考虑：飞书接口给的是当前快照，给不了"这件事被推了三次"。一期必须读取并展示飞书已有日程；AI 生成的日程建议必须先经用户明确同意，才允许创建或修改日历日程，未经同意不得写入。

### 3.2 本地必须存全量的三个理由

| 理由 | 具体 |
| --- | --- |
| **过程无处可查** | 飞书只存当前截止，不知道原来定的哪天。不记流水，"推了三次还没动"永远算不出来 |
| **删除即蒸发** | 清理清单后条目在接口层彻底消失，本地是唯一还留着"它曾经存在过"的地方 |
| **AI 要便宜且完整的上下文** | 生成一次计划要读 30 天完成率、未完成清单、7 天日程密度、目标进度——走接口是几十次调用加限流，走本地是一次查询 |

### 3.3 同步动作

| 动作 | 方向 | 说明 |
| --- | --- | --- |
| 按需同步 | 飞书 → 本地 | 页面打开、生成计划、生成复盘、用户主动刷新时拉取；收到可靠事件时直接更新并记录流水 |
| 写任务计划 | 本地 → 飞书 → 本地 | 用户回复"可以"后写入或更新任务，走 §2.4 时序，成功后回填 ID |
| 写建议日程 | 本地 → 飞书 → 本地 | 先展示时间块和拟创建内容；用户明确同意后创建或修改，成功后回填事件 ID |
| 完成状态 | 飞书 → 本地 | 一期由用户在飞书标记完成，系统只同步状态并写入复盘数据 |

**离线可用**：断网时计划生成、记录撰写、检索、推荐全部可用；写飞书进待补写队列。

**错过触发点的补跑**：启动时若已过当日触发时间——早间计划在 12:00 前补全量，之后只出"下午剩余"并标「补生成」；晚间记录在次日 07:00 前补并标「补记」。

### 3.4 对账的四种结果

| 结果 | 含义 | 处置 |
| --- | --- | --- |
| 一致 | 无事 | 无 |
| 飞书有、本地无 | 同步漏了，或你在别处新建 | 补写本地，流水标 `source=reconcile` |
| 本地有飞书 ID、飞书查不到 | **极可能已被删除** | 标 `deleted_in_feishu`，保留历史 |
| 本地无飞书 ID | **从没写成功过**（欠账） | 重试写入；3 次失败告警 |

区分第三与第四只有一条依据：**有没有飞书 ID**。混在一起会把"你亲手删的"误判成"写失败"，然后反复往飞书重建。

**对账只产出偏差，绝不自动修复。** 接口读失败时**不得**判定为已删除——网络抖一下会清空整个账本。

### 3.5 日程：单一写入者

**日程只在飞书写，本地不留独立日程。** 日程的本质是"时间被占用"，本地也存一份就会重复计算占用 → 可用时长变少 → 计划越排越少，而且不报警。

| 场景 | 做法 |
| --- | --- |
| 你在飞书建的日程 | 只拉取，不复制成"本地日程" |
| 你本机说"明天下午 3 点见客户" | 确认后**直接建成飞书日程**，回填事件 ID |
| 系统建议的时间块 | 确认后写飞书（FR-7），同样回填 ID |
| 你在飞书删了 | 本地标"已消失"，不保留为独立事件 |

**三个必须防的坑**

| 坑 | 表现 | 防法 |
| --- | --- | --- |
| 回环重复 | 写进飞书，下次同步读回来当新事件，每轮翻一倍 | 有事件 ID 的一律视为自己写的，不再写 |
| 两边都改 | 飞书改了，本地也改了 | 以飞书为唯一真相；本地改动先写飞书，写失败就不改本地 |
| 重复日程被展开 | 每周例会是一个规则，不是 N 个事件 | 展开仅用于算未来 7 天占用，**只存规则本身** |

## 4. 计划算法：一天排几件

件数从你的历史里算，不预设数字。模型只能在给定件数内选内容。

```text
基线 = 近 14 天真实完成件数的中位数（无历史时按角色估，默认 3）
      ↑ 近 7 天每天都做完且还接住了临时任务 → +1
      ↓ 近 3 天完成率 < 60% → −1
可用度 = （清醒时长 − 日程占用 − 生活缓冲）÷ 清醒时长
件数 = 基线 × 可用度修正，单日调整幅度不超过 ±1
```

| 要点 | 原因 |
| --- | --- |
| **用"完成"算，不用"计划"算** | 用计划件数会自我强化：计划 5 件做完 3 件，下次还排 5 件，永远学不会 |
| **单日只准动 ±1** | 昨天 5 件今天 2 件，你会觉得它在乱来，然后不再看 |
| **不设死上限，只受时间约束** | 数据支持 6 件就排 6 件；排不下的唯一理由是当天没那么多可用时间 |
| **件数必须写理由，且引用真实数据** | 例：`今天 4 件（近两周平均完成 3.6 件；今天日程占 3 小时，比平时少 1 小时空闲）`。写不出理由即判不合格 |

**会学什么**：星期几的产能差异 / 你以为 vs 实际耗时 / 哪类事总被推迟 / 时间偏好 / 接临时任务的能力。

**冷启动**：无历史时按角色估（默认 3），前 7 天卡片直说"我在摸你的节奏，这几天件数可能不准"。已回灌历史（FR-20）则跳过估算，直接按真实基线，不出现这句说明。

## 5. 角色档案

| 字段 | 必填 | 怎么参与计算 |
| --- | --- | --- |
| 角色名称 | 是 | 决定任务类型权重（架构师 vs 销售的排法不同） |
| 职责范围 | 是 | 超出职责的任务降权，卡片标"可委派" |
| 当前阶段目标（1–3 条） | 是 | 连续 3 天没推进任何目标 → 强制插入 1 件并说明理由 |
| 工作节奏 | 是 | 决定时间块落点，避开会议与生活时段 |
| 每日深度工作时长 | 是 | **只用于冷启动**估件数；7 天真实数据后由产能基线取代 |
| 任务颗粒度偏好 | 否（默认 2 小时） | 决定要不要拆任务 |
| 明确不想做的事 | 否 | 硬过滤，违反即判定规划失败 |

角色变更必须改变输出。验收方式：改参数，看次日件数是否变化（AC-14）。

## 6. 模型池

| 项 | 说明 |
| --- | --- |
| 接入 | 统一走 OpenAI 兼容协议（自定义 base_url + key），至少支持 DeepSeek、Kimi、通义 |
| 分工 | 规划 / 记录撰写 / 消息解析 / 兜底，可各配不同模型 |
| 降级链 | 主模型超时或报错 → 自动切备用，卡片标"本次由备用模型生成" |
| 用量 | 每次记环节、模型、耗时、token、是否降级 |
| 成本上限 | 可设每日 token 上限，超限降级到便宜模型而非直接失败 |

**硬规则**：模型输出只能是"建议"和"文本"，写飞书前必须过结构化校验（标题非空、时间合法、条数不超限）；降级必须可见；所有模型不可用时仍要出**裸排序计划**（按截止 + 顺延次数）并标注。

## 8. 业务规则

| # | 规则 | 违反的后果 |
| --- | --- | --- |
| R1 | **当前态以飞书为准，历史态以本地为准** | 混着用，要么历史被覆盖，要么当前态过期 |
| R2 | **完成状态以飞书为准，完成后回流本地**。一期由用户在飞书手动勾选，系统永不自主勾选，本地永不直接改完成态 | 出现"本地完成、飞书没完成"的假状态，下次同步被改回去 |
| R3 | **任务与日程写入都必须确认**；用户回复"可以"视同同意当前计划及其日程建议 | 日历和任务列表被污染；日程建错会占真实时间，错误被后续规划放大 |
| R4 | 计划件数由历史完成量 + 当日可用时间算出，模型只能选内容 | 模型永远给同一件数，产品退化成固定清单 |
| R5 | 记录的事实部分必须可追溯到任务状态 | 记录变成小说，推荐失去依据 |
| R6 | **写飞书必须幂等，创建前必须查重**：查重第一道，幂等标识第二道 | 重试一次多一个任务，飞书任务列表很快不可用 |
| R7 | 角色变更必须影响输出，不能只是提示词 | 角色变成摆设，产品退化为通用待办 |
| R8 | 模型不可用时退化为裸排序，不得无输出 | 早上打不开，等于产品当天不存在 |
| R9 | **日程单一写入者：只在飞书写，本地不留独立日程** | 重复占用时间，可用时长算错，计划越排越少且不报警 |
| R10 | **对账只出偏差不自动修复；接口读不到时不得判定为已删除** | 自动修复让两边同时不可信；把"读不到"当成"删了"会一次清空账本 |

## 13. 准入与完成标准

**开工（DoR）**：验收可判定（第三方按步骤能得出通过/不通过）· 边界已列（空数据/超限/重复/失败）· 依赖可用（权限、凭据、数据目录）· 数据归属已定 · 不新增未在 §12 记录的选型。

**完成（DoD）**：行为按验收步骤实跑通过 · 至少验证 1 条失败路径且用户可见 · 幂等已实际重放 · 不丢不重不该改的没改 · 失败有原因可定位 · PRD 状态已更新 · 写外部系统的可撤销。

状态四态：**未开始 / 进行中 / 已实现待验证 / 已验证通过**。"已实现待验证"不等于完成。

## 附录 A：接口能力核实（2026-11-05，据飞书开放平台文档）

| 能力 | 结论 | 关键约束 |
| --- | --- | --- |
| 读取任务 | ✅ | 任务查询 + 清单维度过滤；`user_id_type=open_id` |
| 创建任务 | ✅ | `/task/v2/tasks`；可同时设 `tasklists`、`start`/`due`、`reminders`、`members` |
| 写优先级 | ✅ | 走 `custom_fields`，需先在目标清单建 `single_select` 字段（字段归属清单，不归属任务） |
| 幂等创建 | ✅ | 可传 `client_token`（10–100 字符），重复调用不产生重复任务 |
| 完成/取消完成 | ✅ | `PATCH` 设 `completed_at`（设 0 为取消）；对已完成任务再设新时间报 `1470400`，须先归零 |
| 子任务 / 重复任务 | ✅ | 独立子任务接口；`repeat_rule`（RFC 5545 风格） |
| 查询已完成任务 | ✅ 部分 | `GET /task/v2/tasks?completed=true` 带 `completed_at`；**无按完成时间过滤**，只能翻页取全量再本地筛（`created_from/to` 是创建时间） |
| 查询已删除任务 | ❌ | 删除后不可恢复、不可操作，详情返 `1470404`；只能靠事件 `obj_type=7` 感知，历史删除无回溯 |
| 变更历史（改期几次） | ❌ | 详情只有当前值；事件 `task.task.updated_v1` 只给 `task_id` + 通知类型，**不含改前改后值**；且应用维度事件不覆盖客户端手建任务 |
| 读取/创建/删除日程 | ✅ | `/calendar/v4/calendars/{id}/events`，按时间窗查，含参会人 |
| 任务变更事件 | ⚠️ 待真实验证 | 飞书支持事件订阅和企业自建应用 WebSocket 长连接；需在开发者后台确认任务更新事件是否能覆盖用户手动完成，并确认事件内容是否带完成状态。事件不可用时，一期使用页面打开、计划/复盘生成和主动刷新时的按需拉取兜底 |

**两个必须用真实凭据验证的点**：

1. 应用 scopes 是否含 `task:task:write`、`calendar:calendar`——缺一个就卡住对应环节。
2. `tenant_access_token` 与 `user_access_token` 的差别：读写"我个人的任务与日历"通常需要用户身份。**这是最容易在 M1 卡住的地方。**
3. 任务更新事件是否在真实账号下覆盖"用户在飞书客户端勾选完成"，以及事件推送丢失后的按需拉取是否能正确补齐。
