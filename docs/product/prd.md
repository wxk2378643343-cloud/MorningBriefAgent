## 变更控制

1. **版本号规则**：方向推翻 → 大版本（v3.0）；增删需求或改变验收口径 → 次版本（v2.x）；措辞与排版 → 不升版本。
2. **每次实质修改必须同步两处**：正文 + 上面那张版本记录表。只改正文不留记录，视为文档缺陷。
3. **基线 = Git 标签**：每次进入开发（G1 通过）打一个标签 `baseline/BL-xxx`，不落快照文件。任何历史版本的完整原文都可随时取回：`git show baseline/BL-001:docs/product/prd.md`；两版之间的差异：`git diff baseline/BL-001 HEAD -- docs/product/prd.md`。
4. **改了冻结条款怎么办**：在版本记录表追加一行，写清改动与原因；若属需求增删或验收口径变更，升版本号并在下一次 G1 打新标签。
5. **什么情况另起文档**：仅当产品定位被推翻时（如 v2.0 取代 `p0-prd.md`）。日常细化一律在本文件原地迭代。

## 0. 这一版改了什么

上一版把产品定义成"记录层"——先把说过的话存住，再谈计划。这个方向是错的：**你要的不是一个更可靠的记事本，而是一个能替你想、并且直接落到飞书里的助手。**

新版的主线是：

```text
飞书里已有的任务与日程  →  AI 结合你的角色重排  →  写回飞书  →  你在飞书里做  →  系统记录并推荐明天
```

记录不再是终点，是**推荐的输入**。

**v2.1 修订**：本地不再只是"缓存"，而是**账本 + 读模型**。飞书写入与本地写入同时发生，所有读操作只读本地。原因见 §3.3——飞书接口只给当前状态，给不了变更历史。

**v2.2 修订**：日程明确「单一写入者」——只在飞书写，本地不留独立日程（§3.6），并冻结三个防重复规则（§3.7）。

**v2.3 修订**：一天排几件不再预设数字，改为从历史完成量自适应（§4.4）；同时补齐工程落地所需的治理结构（版本记录、追溯矩阵、开工/完成标准、评审清单）。

**v2.4 修订**：判断一、判断二被产品负责人修正——完成可以在对话里宣告（系统代写飞书），任务与日程创建都必须先确认；新增任务查重与"记录先确认再落档"；所有触发时间可配置。

**v2.5 修订**：核实了飞书任务接口的历史数据边界（附录 A）：**已完成任务与完成时间可查**，改期过程与被删任务查不到。据此新增 FR-20 历史回灌——首次启动就把过去的完成记录拉进来算产能基线，不必干等 14 天。

## 1. 需求还原

### 1.1 你的四句话，翻译成产品语言

| # | 你的原话 | 产品含义 | 本 PRD 对应 |
| --- | --- | --- | --- |
| N1 | 利用飞书的任务和日程帮我制定任务和计划 | 飞书不是推送渠道，是**事实源 + 操作面板**。系统读它、改它，而不是另建一套任务库 | §3、§6.1–6.3 |
| N2 | 每天根据我的任务和完成了什么进行记录，然后推荐第二天的事情 | 闭环终点是**次日建议**，记录只是中间产物 | §6.5–6.6 |
| N3 | 我要给他我是什么角色然后进行任务规划 | 规划必须**因人而异**。同样是"3 件事"，架构师和销售的内容不该一样 | §4 |
| N4 | 可以考虑调用多个 AI 平台 | 模型是**可替换零件**，不同环节可用不同模型 | §5 |

### 1.2 三个判断（v2.4 已按产品负责人反馈修正前两条）

**判断一：完成状态只有一条写路径——先写飞书，再回流本地。但"宣告完成"可以在对话里说。**
你在飞书勾完成，或者直接对 AI 说"这件事完成了"，都行。区别只是入口：系统听到宣告后**代你在飞书标记完成**，再从飞书回流本地。关键约束不变：**系统永不自主勾完成**，代勾必须由你的明确指令触发；本地永不直接改完成状态。这样无论你从哪个入口操作，事实源都还是飞书那一个。

**判断二：任务和日程的创建都必须经你确认（v2.4 起，不再区分对待）。**
AI 判定"这是一件事"之后只出确认卡，你回"行"才落飞书。计划采纳（回"行"采纳整张计划卡）视同对该卡内事项的一次性确认，不需要二次确认。防重规则见 R6：创建前先查重，已有的不重建。

**判断三：AI 不负责"编造事实"，只负责"把算出来的事实写成话，并等你确认"。**
"今天完成了什么"由本地数据库的任务状态差分算出（确定性），AI 写成一段人话 + 明天建议；**这张记录卡先给你过目，你确认（或更正）后才落档**。让 AI 自己回忆今天干了什么，等于让它编；不经确认就落档，等于让错误直接进历史。

### 1.3 一句话定位

> **一个懂你角色的计划助手：把你飞书里散着的任务和日程，每天早上排成能做完的一天，晚上告诉你今天实际发生了什么、明天该先动哪个。**

它不是：任务管理工具（飞书已经是了）、笔记软件、新闻聚合器、团队协作平台。

## 2. 核心闭环

```text
① 读        ② 排            ③ 确认        ④ 做            ⑤ 核           ⑥ 记+荐
飞书任务    结合角色与       你确认后      飞书勾完成      AI 从本地库    记录卡给你
飞书日程    当天承载量       写飞书        或对 AI 说      算完成草稿      确认后落档
  ↓           → 今天该做的几件  （任务/日程    "完成了"         → 你确认        ↓
每天可配                  均需确认）                                    明日建议进
（默认 07:00）                                                          次日候选
```

四个时间点构成产品全部节奏，**全部可配置**（默认值如下，见 FR-19）：

| 时间（默认） | 动作 | 用户成本 |
| --- | --- | --- |
| 07:00（可配） | 早间计划卡：今天该做几件（按你的历史节奏定）+ 为什么是这几件 | 看一眼，回"行"或"改：…" |
| 全天 | 随手记：飞书发一句 → 确认卡 → 变成任务/日程 | 说两句话（一句内容、一句确认） |
| 21:30（可配） | 晚间流程：AI 从本地库算出"今天完成了什么"的草稿卡 → **你确认** → 落档 + 明日建议 | 读一遍，回"对"或"改：…" |
| 次日 07:00（可配） | 昨日建议自动进入今日计划候选 | 无需操作 |

**闭环唯一的验收标准**：连续两周，每天早上不需要自己想去做什么，晚上不需要自己回忆做了什么。

## 3. 关键决策：东西到底放在哪

这是本 PRD 最重要的一节，因为它决定后面所有实现成本。

### 3.1 四层归属

| 层 | 载体 | 职责 | 放什么 | 谁写 |
| --- | --- | --- | --- | --- |
| **操作层** | 飞书任务（Task） | 你干活的地方 | 要做的事：标题、截止、优先级、完成状态 | 系统建（需确认）、你勾完成**或对话宣告由系统代勾** |
| **时间层** | 飞书日程（Calendar） | 你被占用的时间 | 会议、约会、专注块 | 你建；系统**确认后**建 |
| **账本层** | 本地数据库 | 系统的记忆与计算底座 | **全量镜像** + 变更流水 + 每日记录 + 计划采纳 + 模型调用 | 系统写，永不丢 |
| **配置层** | 角色档案 + 模型池 | 你是谁、怎么工作、用哪个模型 | 角色 7 字段、模型池与降级链 | 你填一次 |

**关键取舍：计划要落到飞书任务里，但同一份数据必须同时落本地。** 只在本地，你会在两个地方看任务，最后只信一个；只在飞书，AI 就得每次去翻接口，还翻不到历史。

**「方便拿取」是本地库的第一价值，不是顺带的好处**：所有读操作（计划生成、记录撰写、推荐、检索）都只读本地；飞书只在同步时被碰一次。这不只是性能问题——**飞书接口给的是"当前状态"，给不了"变更历史"**，而"这件事被推迟了 3 次"恰恰是推荐的核心依据，只能由本地记出来。

### 3.2 事实源与冲突规则

本地存全量，不等于本地说了算。**要按"当前态"和"历史态"分开定权**——这是本节最重要的一条：

| 数据类别 | 例子 | 事实源 | 理由 |
| --- | --- | --- | --- |
| **当前态** | 任务是否存在、标题、截止、优先级、**是否完成** | **飞书** | 你只在飞书里操作，飞书永远最新 |
| **历史态** | 什么时候完成的、改过几次截止、被顺延几次、哪天进的计划 | **本地** | 飞书只给当前快照，**不提供变更历史**，接口也查不到 |
| **生成物** | 每日计划、每日记录、推荐、模型调用记录 | **本地** | 飞书里没有这些对象 |
| **配置** | 角色档案、模型池 | **本地** | 你改一次，长期不变 |

冲突处理规则：

| 情况 | 处理 |
| --- | --- |
| 本地与飞书当前态不一致 | **飞书覆盖本地**，覆盖前把旧值记一条变更流水（否则丢历史） |
| 飞书任务被你删除 | 本地不删，标记"已消失"，历史保留 |
| 本地有新任务但飞书写入失败 | 本地保留"待补写"状态，重试；不允许只留本地就当成功 |
| 你直接在飞书改了标题/截止 | 下次同步覆盖本地，并记一条"来源：飞书手工修改" |
| 同一任务本地有 2 条记录 | 判定为幂等失效，合并并告警（这是缺陷，不是正常状态） |

### 3.3 为什么本地必须全量写

先纠正一个说法：**"飞书查不到历史"不准确。** 查过接口（附录 A 有记录），准确边界是三条：

| 想知道什么 | 飞书能不能给 | 限制 |
| --- | --- | --- |
| 哪些任务已完成、什么时候完成的 | ✅ 能 | 可按 `completed=true` 过滤，任务对象带 `completed_at`；**但没有"按完成时间"过滤**，只能翻页取全部已完成再本地筛。清单维度有 `created_from/to`，那是**创建时间**，不是完成时间——8 月建、10 月完成的任务查不到 |
| 某条任务改过几次截止、被推过几次 | ❌ 不能 | 任务详情只有当前值。变更事件（`task.task.updated_v1` / `update_tenant_v1`）只给 `task_id` + 通知类型，**不含改前改后的值**，且只从订阅那一刻起算，没有回溯 |
| 被删掉的任务 | ❌ 不能 | 删除即不可恢复，官方原文："删除后无法恢复，也不能对已删除任务做任何操作"。删除只在事件里出现（`obj_type=7`），订阅之前删的永远查不到 |

所以本地必须全量写，理由收敛成三条：

1. **过程无处可查。** "这件事你推了三次还没动"是最该被推荐的判断，而飞书只保存当前截止日期——它不知道原来定的是哪天。**不记流水，这类判断永远算不出来。**
2. **删除即蒸发。** 你清理清单、删掉做废的任务，那些条目在接口层彻底消失。本地账本是唯一还留着"它曾经存在过"的地方。
3. **AI 需要便宜且完整的上下文。** 生成一次计划要读：30 天完成率、未完成清单、近 7 天日程密度、角色目标进度。走接口是几十次调用加限流风险；走本地是一次查询。

**由此派生一条需求（FR-20）**：既然"已完成 + 完成时间"是可批量拉取的事实，首次启动就应当**回灌**一次历史，而不是从零开始攒——否则产能基线要等 14 天才准。

### 3.4 同步策略（拉为主，写双记）

| 动作 | 方向 | 说明 |
| --- | --- | --- |
| 定时同步（默认 10 分钟） | 飞书 → 本地 | 拉取任务与日程当前态，覆盖本地镜像，**差异写流水** |
| 计划写回 | 本地 → 飞书 → 本地 | 先记本地"待写"，写成功后回填飞书 ID 与状态；失败保持待补写 |
| 完成状态 | 飞书 → 本地 | 当前态只读；唯一的写路径是"对话代勾"（R2）：你宣告完成 → 系统写飞书 → 回流本地 |
| 日程/任务写入 | 本地 → 飞书（需确认） | 任务与日程均确认后才写（R3），写入后回填 ID 以便撤销 |

**离线可用**：断网时，计划生成、记录撰写、检索、推荐全部可用（读本地）；只有"写回飞书"和"拉取新状态"会排队等待。

**错过触发点的补跑**：启动时若已过当日触发时间且该动作未执行——早间计划在中午 12:00 前补全量，之后只出"下午剩余"并标注「补生成」；晚间记录在次日 07:00 前补，标注「补记」。机器关了一天，第二天不再是数据黑洞。

### 3.5 本地要存什么

不规定表名与字段类型，只规定必须能被表达的信息：

| 信息 | 作用 | 关键约束 |
| --- | --- | --- |
| 任务镜像（当前态） | 读模型，AI 的唯一入口 | 每条带飞书任务 ID；与飞书同步覆盖 |
| 任务变更流水 | 顺延次数、改期历史 | 只追加不改写；含旧值/新值/来源/时间 |
| 日程镜像与占用统计 | 算可用时长 | 含全天事件标记 |
| 每日计划 | 当天采纳了哪几件、理由 | 含件数与件数理由，便于事后验证规划质量 |
| 每日记录 | 当天实际发生了什么 | 生成后不可改，更正走"次日补记" |
| 推荐与反馈 | 建议了什么、是否被采纳 | 用于"忽略 3 次就不再出现" |
| 角色档案 | 规划输入 | 有版本号，改动要能追溯 |
| 模型调用记录 | 环节/模型/耗时/token/是否降级 | 用于成本与质量归因 |
| 待补写队列 | 写飞书失败的重试 | 必须能重放且幂等 |

**一条底线：本地库可以整目录拷走，换台机器能直接读。** 数据一律用通用格式存放，任何工具都能直接打开。

### 3.6 日程怎么合并：单一写入者原则

先纠正一个说法：**飞书不会主动读你本机的东西。** 能读两边的只有跑在本机的程序——它读飞书日历、读本地数据、合并、再写回飞书。所谓"利用飞书读取本地"实际是"程序把两边揉在一起，然后以飞书为准呈现"。

三种做法，成本差很多：

| 模式 | 含义 | 风险 | 建议 |
| --- | --- | --- | --- |
| **A 单向拉取** | 飞书日程 → 本地镜像 | 无 | 必做（FR-2） |
| **B 合并展示** | 本地已有数据 + 飞书日程 → 统一视图 | 无（只读） | 可做，但本地不应有"独立日程" |
| **C 双向写回** | 本地新建 → 写飞书；飞书改了 → 覆盖本地 | **重复、回环、冲突** | 只在严格规则下做 |

**核心规则：日程只能有一个写入者，就是飞书。**

理由很硬：日程的本质是"时间被占用"。一旦本地也能存一份独立日程，同一天就会被算两次占用——可用时长算错，计划件数跟着错，而且这类错误不会报警，只会让计划越来越保守。

所以本项目采用：

| 场景 | 做法 |
| --- | --- |
| 你已经在飞书里建的日程 | 只拉取，不复制成"本地日程" |
| 你想在本机说一句"明天下午 3 点见客户" | 走飞书卡片确认 → **直接建成飞书日程** → 回填事件 ID 到本地。**本地不保留"只存在于本地的日程"** |
| 系统建议的时间块 | 确认后写成飞书日程（FR-7），同样回填 ID |
| 你在飞书删了某个日程 | 本地标"已消失"，不保留为独立事件，避免幽灵占用 |

### 3.7 合并时必须防的三个坑

| 坑 | 表现 | 防法 |
| --- | --- | --- |
| **回环重复** | 本地建的日程写进飞书，下次同步又读回来当成"新日程"，再写一次 → 每同步一轮翻一倍 | 写完立即回填飞书事件 ID；本地已有 ID 的一律视为"自己写的"，不再写 |
| **两边都改** | 你在飞书改了时间，本地也有一次修改 | 日程以飞书为唯一真相，本地修改一律先写飞书；写失败就不改本地，避免出现"本地改了但飞书没改"的假状态 |
| **重复日程被展开** | 每周例会是一个"重复规则"，不是 N 个事件 | 拉取时按规则展开到"未来 7 天"用于算占用，但**只存规则本身**，不把展开结果当独立日程存下来 |

**这三条不需要额外功能，但必须在 M1 就写死，否则数据会慢慢变脏，而且脏了很难查。**

## 4. 角色档案（N3 的规格）

### 4.1 为什么这是必需品而不是可选项

没有角色，规划只能按"截止时间 + 未完成"排序，输出必然是通用待办清单。有了角色，才可能出现这种差别：

| 场景 | 无角色 | 有角色（前端架构师） |
| --- | --- | --- |
| 同样 5 个未完成任务 | 按截止排序，全塞给你 | 优先排"影响他人进度"的那件；把"写文档"拆成 30 分钟可做的小块塞进会议间隙 |
| 同一天 4 个会 | 只看剩余时长 | 知道会议之间只有 45 分钟，不安排需要连续思考的架构设计 |

### 4.2 角色档案要填什么

| 字段 | 示例 | 是否必填 | 影响什么 |
| --- | --- | --- | --- |
| 角色名称 | 前端架构师 | 必填 | 决定任务类型的权重 |
| 职责范围 | 负责前端架构、组件库、技术选型；不负责后端接口实现 | 必填 | 判断哪些任务"不该我做"，建议委派或推后 |
| 当前阶段目标 | Q4 完成组件库重构、带 1 名新人 | 必填（1–3 条） | 决定长期任务的插入频率 |
| 工作节奏 | 9:30 上班，10–12 点深度工作，下午多为会议 | 必填 | 决定时间块放在哪 |
| 每日深度工作时长 | 3 小时 | 必填 | **只用于冷启动**：前几天没有历史时先估一个件数，之后被真实完成数据覆盖 |
| 任务颗粒度偏好 | 30 分钟 / 2 小时 | 选填（默认 2 小时） | 决定要不要拆任务 |
| 明确不想做的事 | 不排早于 9 点的任务 | 选填 | 硬约束，规划不得违反 |

### 4.3 角色怎么影响规划（必须可验证）

不是"提示词里写一句"，而是**参与计算的参数**：

| 角色字段 | 参与方式 |
| --- | --- |
| 每日深度工作时长 | **只作为冷启动的初始估计**（深度时长 ÷ 颗粒度）；有 7 天以上真实数据后，由历史完成量取代它 |
| 工作节奏 | 决定时间块落点，避开会议与生活时段 |
| 职责范围 | 对超出职责的任务降权，并在卡片上标注"可委派" |
| 当前阶段目标 | 连续 3 天没有推进任何目标 → 强制插入 1 件目标相关任务，并说明理由 |
| 明确不想做的事 | 硬过滤，违反即判定规划失败 |

**验收口径**：把角色档案里的"每日深度工作时长"从 3 小时改成 1 小时，同一天的任务集合必须明显变少。变不了，说明角色只是装饰。

### 4.4 一天排几件：从你的历史里学，不预设数字

**没有固定上限。** 没有"每天 3 件"或"最多 5 件"这种数字。件数由三样东西决定，而且会随你状态变化：

| 输入 | 作用 | 数据来源 |
| --- | --- | --- |
| **产能基线** | 你实际一天能做完几件 | 过去 14 天的真实完成件数（不是计划件数） |
| **当日可用度** | 今天还剩多少可用时间 | 日程占用比例、是否出差/全天会议 |
| **习惯特征** | 你在什么条件下做得多、什么条件下会放弃 | 账本里的长期记录 |

#### 怎么算

```text
基线 = 近 14 天真实完成件数的中位数（新用户先按角色估，默认 3）
      ↑ 若近 7 天每天都做完且当天还接住了临时任务 → +1
      ↓ 若近 3 天完成率 < 60% → −1
      ★ 首次启动已回灌历史（FR-20）时，直接用它算，跳过冷启动估算
可用度 = （清醒时长 − 日程占用 − 生活缓冲）÷ 清醒时长
件数 = 基线 × 可用度修正，单日调整幅度不超过 ±1
```

四个关键点：

1. **基线用"完成"算，不用"计划"算。** 用计划件数会自我强化——你计划 5 件、做完 3 件，下次还按 5 件排，永远学不会。
2. **单日只准动 ±1。** 不加这个阻尼，昨天完成 5 件今天变 2 件，你会觉得它在乱来，然后不再看。
3. **不设死上限，但受时间约束。** 如果数据支持一天 6 件（你确实做完了），就排 6 件；排不下的唯一理由是当天没有那么多可用时间。
4. **件数必须写理由，且理由用你的数据说话**：

```text
今天 4 件
（近两周你平均完成 3.6 件；今天日程占 3 小时，比平时少 1 小时空闲）
```

#### 学什么习惯（长期累积，越用越准）

| 习惯 | 怎么用 |
| --- | --- |
| 星期几的产能差异 | 周一会议多 → 排少且排轻；周三个人高产 → 排重活 |
| 实际任务耗时 | 你以为 2 小时的事实际 4 小时 → 下次同类任务自动折算 |
| 高频被推迟的类型 | 某类事连续被推 3 次 → 少排、或拆成更小的块 |
| 时间偏好 | 你早上完成率明显高于晚上 → 重活默认放上午 |
| 接临时任务的能力 | 经常中途插入新任务还能完成 → 说明还有余量，可略增 |

#### 前 7 天：明确承认"还在学"

- 没有历史时，按角色估一个初始值（默认 3），**前 7 天在初始值上下浮动**，观察你实际完成情况。
- 卡片上直说："我在摸你的节奏，这几天件数可能不准，你直接改。"
- 不装作已经懂你——第一周给出 6 件然后你一件没做，比给 3 件更伤信任。

#### 验收口径

连续 14 天后：**计划件数与当天真实完成件数的偏差不超过 1 的天数，要占到 10 天以上**；同时件数在这 14 天里必须出现过变化（永远同一个数字说明没在学）。

## 5. 多 AI 平台（N4 的规格）

### 5.1 先明确"多"指什么

"调用多个 AI 平台"有两种落地形态，成本差一个数量级：

| 形态 | 含义 | 成本 | 建议 |
| --- | --- | --- | --- |
| **A 可切换** | 配置里选一个，全局生效 | 最低 | 必做 |
| **B 分工** | 不同环节用不同模型（规划用强推理、摘要用便宜、解析用快） | 中 | **第一版就做** |

**第一版采用 A + B。** 计划质量的主要瓶颈是**角色信息与任务上下文不足**，不是模型数量不够。

### 5.2 模型池要能配什么

| 项 | 说明 |
| --- | --- |
| 供应商与模型名 | 至少支持 DeepSeek、Kimi、通义、OpenAI 兼容接口 |
| 接入方式 | 统一走"OpenAI 兼容协议"自定义 base_url + key，避免每家写一套 |
| 承担环节 | 规划 / 记录撰写 / 消息解析 / 兜底 |
| 降级链 | 主模型超时或报错 → 自动切备用，卡片标注"本次由备用模型生成" |
| 用量记录 | 每次调用记：环节、模型、耗时、token、是否降级 |
| 成本上限 | 可设每日 token 上限，超限降级到便宜模型而不是直接失败 |

### 5.3 硬规则

- **模型不允许改事实。** 模型的输出只能是"建议"和"文本"，写入飞书的任务字段必须经过结构化校验（标题非空、时间合法、条数不超限）。
- **降级必须可见。** 用了备用模型要在卡片上写出来，否则你无法判断质量波动来自哪里。
- **可离线**：所有模型都不可用时，系统仍要能出"只按截止时间排序的裸计划"，并标注"AI 不可用"。不允许因为模型挂了就没有计划。

## 6. 功能需求

优先级：**P0 必须**（缺了闭环不成立）、**P1 应该**、**P2 可选**。

### 6.1 接入层

#### FR-1 读取飞书任务并落本地
**故事**：作为用户，我不希望重新录一遍任务——飞书里已有的就该被用上；同时我希望这些数据在本机能随时查、随便算。

- 读取指定任务清单（或全部未完成）的任务：标题、截止时间、完成状态、优先级、描述。
- 增量读取，不要求每次全量拉取；能识别"被我在手机上新建的任务"。
- **读到就落本地**：更新本地镜像，并把"和上次不一样的地方"写成变更流水（截止改了、标题改了、完成了）。
- 对飞书侧只读，不改。

**边界**：任务数千条时只取未完成 + 近 30 天已完成；无截止时间的任务归入"池子"而非"今天"；飞书任务被删 → 本地标"已消失"，历史保留。

**验收**：AC-1 — 在飞书手建 3 个任务（含 1 个无截止），10 分钟内系统全部可见，字段与飞书一致；**断开飞书接口后，本地仍能查到这 3 条**。

#### FR-2 读取飞书日程
**故事**：作为用户，我希望系统知道我今天有几个会、还剩多少可用时间。

- 读取今日与未来 7 天日程：开始/结束、标题、是否全天、参与人数。
- 用于计算"可用时长"，不用于生成任务。

**边界**：全天日程（出差/休假）→ 可用时间接近零，当天只排 1 件最要紧的事；连续会议间隔 < 30 分钟视为不可用；重复日程（每周例会）按规则展开到未来 7 天用于算占用，但**只存规则本身**，不把展开结果当独立日程存；系统自己写进去的日程靠事件 ID 识别，不得当新事件再处理（§3.7）。

**验收**：AC-2 — 今日有 4 个日程，系统算出的可用时长与手工计算误差 ≤ 15 分钟。

#### FR-3 统一待办池
**故事**：作为用户，我想要一个"所有该做的事"的合并视图，而不是在两个列表间切换。

- 合并：飞书未完成任务 + 飞书未来日程 + 系统临时捕获项。
- 每项标注来源，可回溯到飞书原条目。
- 本地只做展示与排序，**不产生新的任务实体**。

**验收**：AC-3 — 池中每一项都能点开跳回飞书对应条目。

#### FR-20 历史回灌（首次启动的一次性动作）
**故事**：作为用户，我不想从零攒 14 天数据才看到像样的计划——过去做完的事，飞书其实还留着。

- 首次接入时，翻页拉取**全部已完成任务**（`completed=true`，每页 100，按接口限流节流），提取 `guid / 标题 / completed_at / 所属清单 / 创建时间`，写入本地账本，标记 `backfilled=true`。
- 回灌是**一次性**的，之后不再重复拉全量；可手动触发"重新回灌"（比如补了旧数据），重复回灌按 `guid` 覆盖，不产生重复行。
- 回灌数据只用于统计与推荐（产能基线、完成趋势），**不进入"今天该做什么"的候选**。
- 回灌失败不影响正常使用：计划与记录照常，卡片提示"历史还在补，件数暂时保守"。
- 明确边界：**已删除的任务无法回灌**（接口不可达），历史里缺的就是缺的，不做猜测补全。

**验收**：AC-21 — 首次接入后，本地能按 `completed_at` 统计出"过去 30 天完成件数"，且与飞书客户端手工计数一致（误差 0）；重复执行回灌后行数不变。

### 6.2 计划层

#### FR-4 早间计划生成
**故事**：作为用户，我早上只想知道"今天做哪几件"。

- 每日 07:00（可配）生成一张卡片：日期、件数及理由、每件事的标题/时间建议/为什么是它。
- 件数由**近 14 天真实完成量 + 当日可用时间**算出（§4.4），**不由模型自由决定**——模型只能在给定件数内选内容。
- 卡片必须显示件数理由，且理由引用的是你的真实数据（"近两周平均完成 3.6 件"），写不出理由即判为不合格。

**边界**：无任何任务时不出计划卡，改为"今天没有待办，要加一件吗"；AI 全挂时出裸排序计划并标注。

**验收**：AC-4 — 连续 14 天，计划件数与当天真实完成件数偏差 ≤1 的天数 ≥10 天；期间件数出现过变化；**未回灌历史时**前 7 天卡片上出现"还在摸你的节奏"的说明，**已回灌时**首次生成就按真实基线且不出现该说明。

#### FR-5 计划写回飞书任务
**故事**：作为用户，我采纳计划后希望它在飞书任务里就是今天的待办，而不是还留在聊天里。

- 采纳后：为每件事确保在飞书有对应任务（已有则更新截止/优先级，没有则新建）。
- **创建前查重**：新建前先在本地账本查未完成任务——标题相同或高相似即视为已存在，走"更新"而不是"新建"，并在卡片注明"已存在，未重复创建"。
- **幂等**：同一件事重复采纳不得产生重复任务；重复投递靠唯一标识识别，不靠标题猜（查重是第一道，幂等标识是第二道）。
- 写回失败要明确告知，并保留"本地待重试"状态。

**验收**：AC-5 — 同一计划采纳 3 次，飞书任务数不变；断开网络采纳 1 次，恢复后能补写且不重复；**飞书已有同名未完成任务时采纳计划，任务数不变且卡片说明"已存在"**。

#### FR-6 时间块建议
**故事**：作为用户，我希望系统告诉我"这件事放在几点做"，而不是只给一个清单。

- 依据日程空档与角色节奏，为每件事建议时间块（起止时间）。
- 时间块与已有日程冲突时不得建议，必须重算。
- 只建议，不直接写日程（见 FR-7）。

**验收**：AC-6 — 建议的 3 个时间块与当日日程零重叠。

#### FR-7 日程写入需确认
**故事**：作为用户，我不接受 AI 擅自占用我的日历。

- 时间块写进飞书日程属于**破坏性操作**，必须先有一次确认（一次点击或一句"可以"）。
- 确认前只在卡片里展示，不落日历。
- 写入后要能撤销（删除该日程）。
- 写入成功后**立刻回填飞书事件 ID 到本地**；已有 ID 的日程永不再写一次（防回环，§3.7）。
- 写飞书失败时，本地不得先改状态，避免出现"本地改了、飞书没改"的假象。

**验收**：AC-7 — 未确认时飞书日程无新增；确认后新增且可撤销；连续 3 次同步后，该日程在飞书仍只有 1 条。

### 6.3 执行层

#### FR-8 完成状态回流与对话完成
**故事**：作为用户，我既可以在飞书里勾完成，也可以直接对 AI 说一句"完成了"，两条路都该通，且结果一致。

- **回流**：定时（或事件驱动）读取任务完成状态，更新本地快照。识别"完成时间"用于晚间记录排序；拿不到完成时间时用同步时间兜底并标注。
- **对话完成**：你对 AI 说"X 完成了"→ 系统在**飞书侧**标记该任务完成（带幂等标识）→ 成功后本地随正常同步回流。系统只在你明确宣告时代勾，**永不自主勾完成**。
- 本地永远不直接改完成状态——两条入口、一条写路径（先飞书、后本地，R2）。
- 代勾失败（网络/权限）必须回卡片说明，任务保持未完成原状。

**验收**：AC-8 — 在飞书勾完成 1 个任务，10 分钟内本地状态同步，记录中出现该完成项；**对 AI 说"另一个完成了"，飞书中该任务被标记完成，且本地同样回流，两条路径结果一致**。

#### FR-9 随手捕获（先确认，再创建）
**故事**：作为用户，我路上想到一件事，不想打开任何 App；但我也不想要 AI 擅自建出来的东西。

- 飞书发一句 → 系统判定是"新任务 / 新日程 / 补充已有任务 / 纯记录"，回一张**确认卡**（含判定结果、拟创建的内容、查重结果）。
- **你确认后才创建**（任务与日程一视同仁，R3）；不确认不落飞书。
- **创建前查重**：与本地未完成任务比对，标题相同或高相似 → 卡片直接提示"已有类似任务：……"，你选择"就是它（更新）"或"确实新建"。
- 判定为新任务时，可一键"建成飞书任务"。
- 能识别"这个放到周五"这类相对时间。

**验收**：AC-9 — 连发 5 句话，≥4 句被正确判定类别，且原文一字不差保留；**未确认时飞书无任何新增；对已存在任务说同类内容，卡片提示了已有条目且默认不重复创建**。

### 6.4 记录层

#### FR-10 每日记录：先确认，再落档
**故事**：作为用户，我想晚上看一段话就知道今天发生了什么，而不是自己回忆；但我也不想错误的内容直接进历史。

- 21:30（可配）AI 从**本地数据库**算出草稿卡：完成清单（真实完成时间排序）、未完成项及其顺延天数、日程实际占用、明日建议预告。
- **内容必须由数据算出**：完成项来自任务状态，不允许模型凭上下文推测。
- **草稿先给你确认**：回"对"→ 落档；回"改：…"→ 按更正修订后落档（你的更正与原草稿都留痕）。
- 未确认时的兜底：超过确认截止（默认 22:30，可配）自动落档并标注"未确认"，次日可在记录页补正——**闭环不因为你没回复就断**。
- 硬限 400 字；不评价、不打分、不写"你很棒/你需要改进"。
- 确认落档后同时存本地 Markdown。

**边界**：当天 0 完成 → 记录仍要生成，写"今日无完成项"，并列出未完成原因候选（超时/被会议占满/主动放弃），不给结论。

**验收**：AC-10 — 连续 7 天，记录中的完成项与飞书实际状态**逐条一致**，无编造、无遗漏；**每条记录都能查到你的确认动作或"未确认"标注；更正过的记录保留原草稿**。

#### FR-11 记录存档与检索
**故事**：作为用户，我希望三个月后能翻回某一天看当时记了什么。

- 按天存档，可按日期范围浏览，可按关键词搜。
- 记录不可编辑（事实一旦生成即为存档）；需要更正时以"次日补记"方式追加。

**验收**：AC-11 — 任取 30 天前的记录，5 秒内打开，内容与当日生成一致。

### 6.5 推荐层

#### FR-12 次日推荐
**故事**：作为用户，我希望晚上那张卡的最后一行告诉我"明天先动哪个"。

- 给出 1–3 条建议，每条含：哪件事、为什么排它（截止/顺延次数/目标关联/依赖他人）。
- 建议必须能在次日 07:00 被直接采用为计划候选。
- 被反复推迟（≥3 次）的任务必须出现，不允许悄悄消失。

**验收**：AC-12 — 连续 10 天，≥7 天的第一条建议在次日被实际采纳。

#### FR-13 推荐采纳与反馈
**故事**：作为用户，我采纳或忽略建议都应该被记住，否则系统永远学不会。

- 采纳 → 进次日计划；忽略 → 记录忽略原因（不追问，从行为推断）。
- 被忽略 3 次的建议不再重复出现，转而询问"这件事还要做吗"。

**验收**：AC-13 — 连续忽略同一建议 3 次后，第 4 天不再出现，且有一次确认询问。

### 6.6 配置层

#### FR-14 角色档案
见 §4。**验收**：AC-14 — 冷启动期（<7 天数据）改"每日深度工作时长"、成熟期改产能基线，两种情况次日计划件数都随之变化。

#### FR-15 模型池与分工
见 §5。**验收**：AC-15 — 主模型故意配错 key，系统自动降级并在卡片标注，计划仍能产出。

#### FR-16 失败可见与幂等（横切）
- 任何写飞书失败、模型失败、同步失败，必须在卡片或页面明确出现，不允许只落日志。
- 所有写操作幂等：重试不产生重复任务、重复日程、重复记录。

**验收**：AC-16 — 构造 4 类失败（任务写失败、日程写失败、模型超时、网络断），4 类都在用户侧可见。

#### FR-17 本地账本：离线可读、可搬移、可导出

**故事**：作为用户，我希望断网也能看能算，也希望这些数据永远属于我、随时能拷走。

- **离线可用**：断网时计划生成、记录撰写、检索、推荐全部可用（只读本地）；写飞书的动作进待补写队列。
- **可搬移**：整个数据目录拷到另一台机器，记录、任务历史、附件路径全部可用（不存绝对路径）。
- **可导出**：一键导出为按天分文件的 Markdown + 一份任务历史 CSV，任意编辑器可开。
- **可查历史**：能回答"这件事被推迟过几次""上周完成了多少"这类问题，且不需要连飞书。

**验收**：AC-17 — 拔网线后完成一次"生成计划 → 撰写记录 → 搜索历史"全流程；把数据目录拷到另一路径启动，历史记录与统计结果一致；导出文件用记事本打开不乱码。

#### FR-18 同步不打架

**故事**：作为用户，我不希望本地和飞书各说一套。

- 定时同步以飞书当前态为准，覆盖前写流水（§3.2）。
- 本地有待补写时，同一任务不得被同步覆盖掉待写字段，避免"刚改完又被拉回去"。
- 同步失败不影响本地可用，只标记"数据可能过期"并显示上次成功时间。

**验收**：AC-18 — 本机改截止后立即断网，等一次同步周期，本地改动不被回滚；恢复网络后飞书收到该改动，且无重复。

#### FR-19 节奏可配置
**故事**：作为用户，我的作息自己定，四个触发点不该写死在代码里。

- 四个时间点全部可配：早间计划（默认 07:00）、晚间记录（默认 21:30）、记录确认截止（默认 22:30）、次日建议并入（默认次日 07:00，与早间共用）。
- 配置改动当日生效（已过的触发点不补跑，次日按新时间执行；补跑规则见 §3.4「错过触发点的补跑」）。
- 时间格式支持 `HH:MM`，按本地时区解释。

**验收**：AC-20 — 把晚间记录从 21:30 改为 20:00，当日生效（若已过 20:00 则次日生效并在卡片说明）；记录确认截止随之联动。

## 7. 关键业务规则

| # | 规则 | 违反的后果 |
| --- | --- | --- |
| R1 | **当前态以飞书为准，历史态以本地为准** | 混着用，要么历史被覆盖，要么当前态过期 |
| R1b | 本地必须存全量，读操作只读本地 | 每次算推荐都去翻接口，慢且算不出历史 |
| R2 | **完成状态只有一条写路径：先写飞书，再回流本地**。系统可以按你的明确宣告代勾（对话里说"完成了"），但永不自主勾完成，本地永不直接改完成状态 | 本地直接改会出现"本地完成、飞书没完成"的假状态，下次同步又被改回去 |
| R3 | **任务与日程写入都必须确认**（计划采纳视同对该卡内事项的一次性确认） | 日历和任务列表被 AI 污染；日程建错会占真实时间，错误被后续规划放大 |
| R4 | 计划件数由**历史完成量 + 当日可用时间**算出，模型只能选内容 | 模型永远给同一个件数，产品退化成固定清单 |
| R5 | 记录的事实部分必须可追溯到任务状态 | 记录变成小说，推荐失去依据 |
| R6 | **写飞书必须幂等，创建前必须查重**：查重（本地未完成任务比对）是第一道，幂等标识是第二道 | 重试一次多一个任务，或者"想到的事"反复建成重复条目，飞书任务列表很快不可用 |
| R7 | 角色变更要影响输出，不能只是提示词 | 角色变成摆设，产品退化为通用待办 |
| R8 | 模型不可用时退化为裸排序，不得无输出 | 早上打不开就等于产品当天不存在 |
| R9 | **日程单一写入者：只在飞书写，本地不留独立日程** | 两边都存会重复占用时间，可用时长算错，计划越排越少且不报警 |

| AC-14 | 角色有作用 | 冷启动期改深度时长；成熟期改产能基线 | 两种情况次日件数都随之变化 | FR-14/§4.4 |

| AC-17 | 本地账本可用 | 拔网线跑全流程 + 拷目录 + 导出 | 三项全通 | FR-17 |
| AC-18 | 双写不打架 | 改后断网，等同步，再恢复 | 改动不被回滚，无重复 | FR-18 |
| AC-19 | 日程不繁殖 | 确认写入后连做 3 次同步 | 飞书该日程仍 1 条；本地无"独立日程" | FR-2/FR-7 |
| AC-20 | 节奏可配置 | 改晚间记录时间 | 当日或次日生效并说明；确认截止联动 | FR-19 |
| AC-21 | 历史回灌准 | 首次接入后统计近 30 天完成数 | 与飞书手工计数一致；重复回灌行数不变 | FR-20 |

**全局验收（连续两周后判定）**

1. 14 天里，早上不需要自己想去做什么（≥12 天直接采纳计划）。
2. 14 天里，晚上不需要自己回忆做了什么（记录与飞书一致，且你看完没有"这不对"）。
3. 飞书任务列表里没有重复项、没有系统建的僵尸任务。
4. 至少发生过一次"AI 建议的事你本来没想到"，且那件事确实该做。
5. 全程不需要打开任何本地页面（本地页面只用于配置与检索）。

第 5 条是新版最重要的变化：**主入口是飞书，本地页面不是必需品**。

## 9. 里程碑

| 阶段 | 交付 | 周末唯一验收 |
| --- | --- | --- |
| **M1 接通**（1 周） | 读任务、读日程、**历史回灌**、落本地账本、算可用时长、出裸排序计划卡 | 飞书里手建的任务能出现在早间卡片里；过去 30 天完成数与飞书一致；**拔网线后仍能查到并出计划** |
| **M2 会排**（1–2 周） | 角色档案 + 计划生成 + 写回任务（幂等） | 连续 3 天，采纳计划后飞书里就是今天的待办，无重复 |
| **M3 会记**（1 周） | 完成回流 + 晚间记录 + 次日推荐 | 连续 5 天，记录与飞书勾选逐条一致，推荐有理由 |

## 10. 风险

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 飞书任务 API 能力不足 | 无法写优先级/自定义字段，写回只能改标题 | **已核实不成立**：任务 v2 支持 `custom_fields`（可在清单上建"优先级"单选字段）、`tasklists`、`client_token` 幂等令牌、`repeat_rule` 重复任务与子任务。M1 第一天仍需用真实凭据跑一次写入验证 |
| 日程写入污染日历 | AI 建的块占掉真实时间 | R3 强制确认 + 可撤销 |
| 计划件数被模型架空 | 每天都给同样件数，理由千篇一律 | 件数由历史完成数据算（§4.4），理由必须引用真实数据，写不出即判不合格 |
| 记录变成小说 | 完成项与飞书不符 | 事实部分只允许来自任务状态；连续 7 天逐条比对（AC-10） |
| 重复建任务 | 飞书里出现一堆同名任务 | 幂等靠唯一标识，不靠标题（R6/AC-5） |
| 双写打架 | 本地改完被同步回滚，或本地版本过期 | 待补写优先于同步覆盖（FR-18）；冲突必写流水 |
| 本地账本退化成缓存 | 只存当前态、不存流水，于是永远算不出"推迟几次" | 镜像与流水是两件事，流水只追加不改写（§3.3/§3.5） |
| 角色形同虚设 | 填了角色，输出没变化 | AC-14 用"改参数量"的方式验收 |
| 多模型变成多麻烦 | 每个环节都超时 | 第一版采用可切换 + 分工；统一 OpenAI 兼容协议 |
| 范围回潮 | 又想做新闻、健康、文件管理 | 一律以"是否让今天这几件事更准"为唯一标准 |

## 14. 开工标准与完成标准

工程落地最常见的失败不是做错，而是**在需求没说清时就开始写**，以及**写完自己宣布完成**。所以两头都要有硬门槛。

### 14.1 开工标准（Definition of Ready）

一条需求只有同时满足以下 6 条，才可以进入开发：

1. 需求编号与验收编号已分配，并在 §13 矩阵中占位。
2. 验收标准是**可判定的**——由第三方按步骤操作能得出"通过/不通过"，不含"体验良好"这类词。
3. 边界条件已列（空数据、超限、重复、失败），且每条都写了期望行为。
4. 依赖已确认可用（飞书权限、模型凭据、数据目录），不可用的已明确降级路径。
5. 数据归属已定（飞书 / 本地 / 两者），写入方向与冲突规则明确。
6. 该需求**不新增未在 §11 记录的技术选型**；若必须新增，先补决策项再开工。

### 14.2 完成标准（Definition of Done）

一条需求只有同时满足以下 7 条，才可以标记为"完成"：

1. **行为**：按 §4 的验收步骤实际操作通过，不是只跑通代码。
2. **失败路径**：至少验证 1 条失败场景（写飞书失败 / 模型超时 / 网络断），且用户侧可见。
3. **幂等**：同一操作重复执行不产生重复数据，并已实际重放验证。
4. **数据**：不丢、不重复、不该改的字段没被改（原文、附件、历史流水）。
5. **可观测**：失败时卡片或页面有原因，日志能定位到具体环节。
6. **文档**：PRD 的验收状态从"未实现"更新为"已验证"，并记录验证日期与方式。
7. **可回滚**：若涉及写外部系统（飞书任务/日程），能撤销或清理已写入的数据。

状态只有四种：**未开始 / 进行中 / 已实现待验证 / 已验证通过**。"已实现待验证"不等于完成。

## 附录 A：接口能力核实（2026-11-05，据飞书开放平台文档）

写 PRD 前先确认了"能不能做"，避免规格落空。

| 能力 | 结论 | 关键约束 |
| --- | --- | --- |
| 读取任务 | ✅ | 任务查询 + 清单（tasklist）维度过滤；`user_id_type=open_id` |
| 创建任务 | ✅ | `/task/v2/tasks`；可同时设置 `tasklists`、`start`/`due`、`reminders`、`members` |
| **写优先级** | ✅ | 走 `custom_fields`：需在目标清单上先建一个 `single_select` 字段（如"优先级：高/中/低"），字段归属清单，不归属任务 |
| **幂等创建** | ✅ 官方支持 | 创建任务可传 `client_token`（10–100 字符），重复调用不产生重复任务——FR-5 的幂等不靠自己拼去重逻辑 |
| 子任务 | ✅ | 有独立"创建子任务"接口，可支撑任务拆分 |
| 重复任务 | ✅ | `repeat_rule`（RFC 5545 风格），可支撑"每周复盘"这类周期事 |
| 更新/完成/删除任务 | ✅ | 完成 = `PATCH` 把 `completed_at` 设为时间戳（设 0 为取消完成）；对已完成任务再设新时间会报 `1470400`，需先归零再重设。FR-8 的"对话代勾"依赖这个接口 |
| **查询已完成任务（历史回灌）** | ✅ 部分满足 | `GET /task/v2/tasks?completed=true`，任务对象含 `completed_at`；**无"按完成时间"过滤**，只能翻页取全量再本地筛。清单维度 `created_from/to` 按**创建时间**过滤，不是完成时间 |
| **查询已删除任务** | ❌ | 官方原文：删除后不可恢复、也不能对已删除任务做任何操作；详情返回 `1470404`。删除只能通过事件感知（`obj_type=7`），历史删除无法回溯 |
| **变更历史（改期几次）** | ❌ | 任务详情只有当前值；事件 `task.task.updated_v1` 只给 `task_id` + 通知类型，**不含改前/改后值**；且应用维度事件只覆盖本应用创建的任务，客户端手建的不推 |
| 读取日程 | ✅ | `/calendar/v4/calendars/{id}/events`，按时间窗查询，含参会人 |
| 创建/删除日程 | ✅ | 支持建事件、加参会人、删事件——FR-7 的"确认后写入 + 可撤销"有实现基础 |

**两个仍需真实凭据验证的点**（文档写了但环境相关）：

1. 自建应用的能力范围（scopes）是否已包含 `task:task:write`、`calendar:calendar`、`base:record:*`——缺一个就卡住对应环节。
2. `tenant_access_token` 与 `user_access_token` 的差别：读写"我个人的任务与日历"通常需要用户身份，而租户身份只能操作应用自己的资源。**这是最容易在 M1 卡住的地方**，第一天就要验证清楚。
