# 交付流程：从一条需求到一次上线

- 版本：v1.0
- 日期：2026-11-05
- 适用范围：本仓库全部产品需求
- 关联：`docs/product/prd.md`（需求基线）、`docs/product/README.md`（文档索引）

> 这份文档解决一个问题：**怎么保证"写进 PRD 的东西"最后真的在跑，而不是写完就结束。**
> 单人项目的流程不需要复杂，但每个阶段必须有明确的"进不去"和"出不来"的条件。

---

## 1. 全景

```text
① 需求收集        ② PRD 基线        ③ 技术方案        ④ 任务拆分
  口述/抱怨/观察  →  编号+验收+追溯  →  数据/接口/失败  →  WBS+依赖
                                                        ↓
   ⑥ 归档复盘   ←   ⑤ 迭代开发 + 验收  ←  ────────────────
```

四道门禁，卡在阶段之间。**门禁不过不进入下一阶段**，宁可在文档上多花半天，也不要在代码上返工三天。

| 门禁 | 位置 | 一句话判定 |
| --- | --- | --- |
| **G1 可开工** | PRD → 技术方案 | 每条需求都能被第三方判定"过/不过" |
| **G2 可编码** | 技术方案 → 任务拆分 | 数据归属、失败路径、幂等规则都已明确 |
| **G3 可交付** | 开发 → 验收 | 完成标准 7 条全部满足，且验证日志已写 |
| **G4 可收尾** | 验收 → 归档 | 需求文档状态与代码一致，无未披露限制 |

---

## 2. 阶段一：需求收集

**入口**：任何来源的原始诉求（自己的想法、使用中的不爽、外部参考）。

**活动**：
- 只记录**问题**，不记录方案。"早上不知道先做哪件"是问题；"加个优先级字段"是方案，方案要晚一步再定。
- 追问三件事：什么场景发生、现在怎么凑合、不解决会怎样。

**产物**：一句话问题陈述（不进 PRD）。

**出口**：能说清"谁在什么情况下遇到了什么麻烦"，否则不进入 PRD。

**常见失败**：把方案当需求记下来，后面围绕错误方案做了三个月。

---

## 3. 阶段二：PRD 基线（对应文件 `prd.md`）

**入口**：问题陈述清晰。

**活动**：
1. 编号：每条需求分配 `FR-x`，每条验收分配 `AC-x`。
2. 写验收：必须是可执行步骤 + 可判定结果。**"体验流畅"不是验收，"点击后 2 秒内出现内容"才是。**
3. 写边界：空数据、超限、重复、失败，四种情况各写期望行为。
4. 写追溯：填完 §13 追溯矩阵，每一行都要有阶段、交付物、验证方式。
5. 自评 §15 评审清单。
6. **冻结基线**：按 `docs/product/baseline/README.md` 复制快照、记录 SHA256、填写基线记录（可被证伪的假设 + 未决项），提交并打 Git 标签 `baseline/BL-xxx`。

**产物**：`docs/product/baseline/BL-xxx-PRD-….md`（只读快照）+ `BL-xxx-record.md`（假设与变更登记）。

**出口（G1 可开工）**：
- 追溯矩阵无空格；
- 评审清单 10 条全"是"；
- 待决策项都有建议值（可被否决，但不能空着）；
- **基线已冻结**，快照的 SHA256 已记录，正文状态置为"已基线"。

**常见失败**：验收写成愿望；边界只写正常情况；需求与验收对不上号。

---

## 4. 阶段三：技术方案

**入口**：G1 通过。

**活动**（只写必要部分，不写实现细节）：
1. **数据归属**：每类数据谁是事实源、写入方向、冲突谁赢。
2. **接口清单**：需要调用的外部接口、需要提供的内部接口，各自失败时返回什么。
3. **幂等设计**：每个写操作怎么保证重复执行不出双份。
4. **失败处置**：超时、部分成功、凭据失效、网络中断，各自的表现与恢复路径。
5. **跨平台**：路径、编码、时区、进程常驻的处理方式。
6. **不做的取舍**：明确本阶段不引入的复杂度（写进方案，不写进 PRD）。

**产物**：`docs/tech/<feature>-design.md`。

**出口（G2 可编码）**：
- 每条 FR 都能在方案里找到落点；
- 每个写操作都有幂等方案；
- 每个外部依赖都有降级行为。

---

## 5. 阶段四：任务拆分

**入口**：G2 通过。

**活动**：
- 按"可独立验证的最小单元"拆，不按"文件"拆。一个任务应该能在半天内做完并自测。
- 每个任务标注：关联需求编号、依赖前置任务、完成的判定方式。
- 排出顺序：**先打通一条最窄的端到端链路**（读 1 条任务 → 出 1 张卡），再补宽度。

**产物**：`docs/plan/wbs.md`（或 Issue 列表），每个任务带 `FR-x` 标签。

**出口**：
- 没有"研究一下"这类无法判定完成的任务；
- 第一个任务能在当天看到可观察结果。

---

## 6. 阶段五：迭代开发与验收

**入口**：任务已拆，G2 已过。

**活动**：
1. 开发时同步写验证脚本（不是事后补）。
2. 每个任务完成时立刻按 §14.2 的完成标准自检 7 条。
3. 阶段末做一次**真实使用验收**：用自己的真实数据跑完整闭环，不用测试数据。
4. 记录摩擦日志：哪一步卡住、卡了多久、当时想做什么。**只记录，不顺手改代码。**

**产物**：验收记录（附日期、操作步骤、实际结果）。

**出口（G3 可交付）**：
- §14.2 七条全满足；
- 每条 AC 有"通过/不通过"的明确结论和证据；
- 未通过项已明确是缺陷还是需求变更。

**常见失败**：用"测试跑通了"代替"人用了一遍"；验收时才发现需求理解错。

---

## 7. 阶段六：归档与复盘

**入口**：G3 通过。

**活动**：
1. 更新 PRD 里每条 AC 的状态（未实现 → 已验证），写验证日期。
2. 更新版本记录表。
3. 摩擦日志里的问题，分流成三类：**缺陷**（进下个迭代）、**需求变更**（走变更流程）、**暂不处理**（记下理由）。
4. **基线复盘**：打开当前基线的 `BL-xxx-record.md`，逐条判定第 3 节的假设成立与否，填第 5 节复盘三问；把结论写回记录文件（结论区只追加）。
5. 归档：过期文档移入 `docs/product/archive/`；冻结快照留在 `baseline/` 不归档（它是长期证据）。

**出口（G4 可收尾）**：
- 文档状态与代码一致；
- 没有"文档说做了、代码里没有"的条目；
- **假设清单逐条有结论**，被证伪的已定位到具体 FR/AC 与返工量；
- 下个阶段的输入已经明确（下一份基线要改哪几条）。

---

## 8. 变更流程

需求一定会变。关键不是禁止变化，而是**让变化有成本、可追溯**。

| 变更类型 | 判定 | 走法 |
| --- | --- | --- |
| **措辞修正** | 不改变验收判定 | 直接改，不升版本 |
| **细节补充** | 增加边界或明确歧义，验收整体不变 | 升次版本，更新版本记录表 |
| **需求增删** | 新增/删除 FR，或改变验收口径 | 升次版本 + 更新追溯矩阵 + 重新基线 |
| **方向推翻** | 产品定位变化 | 升大版本，旧文档降级归档 |

三条硬规则：

1. **口头加需求不生效。** 必须落到 PRD 的 FR 与 AC 上，否则视为没提。
2. **范围扩大必须同时给出删减项。** 加一件事，就要说清哪件事往后放——否则进度必然崩。
3. **返工是变更，不是缺陷。** 因需求理解错导致的返工，先改文档再改代码，否则同样的错会再犯一次。

## 9. 单人项目的角色兼任

一个人做，仍然要**在时间上把角色分开**，不能同时当作者和验收者：

| 角色 | 什么时候做 | 关键纪律 |
| --- | --- | --- |
| 产品 | 写 PRD 阶段 | 只写"要什么"，不替实现做决定 |
| 架构 | 技术方案阶段 | 只解决数据归属与失败路径，不美化 |
| 开发 | 迭代阶段 | 不顺手改需求；卡住先记摩擦日志 |
| 验收 | 阶段末，隔至少半天 | 必须用真实数据、按文档步骤走，不看代码 |

**最容易被跳过的是"隔半天再验收"**。刚写完代码就去验，验的是自己的记忆，不是产品行为。

---

## 10. 每阶段的度量

不追速度，追"返工率"。四项足够：

| 指标 | 怎么算 | 红线 |
| --- | --- | --- |
| 需求返工率 | 因需求理解错而重做的任务数 ÷ 总任务数 | > 20% 说明 PRD 阶段没做够 |
| 验收一次通过率 | 首次验收通过的 AC 数 ÷ 总 AC 数 | < 70% 说明完成标准形同虚设 |
| 缺陷逃逸数 | 验收后才发现的数据类问题 | 出现 1 个就要查幂等与失败路径 |
| 摩擦日志条数 | 每阶段记录的真实卡点数 | 为 0 说明没真用，不是产品没问题 |

## 11. 与 PRD 的对应关系

| PRD 内容 | 在本流程中的位置 |
| --- | --- |
| §1 需求还原 | 阶段一的产物沉淀 |
| §6 功能需求 FR | 阶段二的编号主体 |
| §8 验收矩阵 AC | 阶段二的判定依据、阶段五的验收脚本 |
| §13 追溯矩阵 | G1 门禁的检查表 |
| §14 开工/完成标准 | G1 与 G3 的具体条款 |
| §15 评审清单 | G1 的自查表 |
